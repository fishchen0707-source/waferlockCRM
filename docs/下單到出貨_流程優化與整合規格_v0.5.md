## 一頁摘要

我們要把「業務發 mail → 助理進 ERP 下單 → 主管在 BPM 簽核 → 助理打出貨單 → 出貨 → 倉庫」
這條**目前全靠人工與 ERP 的流程**，用 Google Apps Script（GAS）簡化成一條有系統支撐、
有通知、有軌跡的流程。

其中「主管在 BPM 簽核」這一環，我們用一個**最小的手段**接進來：
請 BPM 在既有的簽核通知信之外，**多寄一份副本**到一個專用信箱，
GAS **只讀這封信**、解析後在 Chat 上 @提及該主管、附上那筆待簽單的直達連結。
主管點一下、登入 BPM、**在 BPM 原生完成簽核**。

**這一版（v0.5）刻意不碰 ERP／BPM 的任何 API。**
不改 BPM 流程、不改 ERP、不動任何主管的個人信箱、不代替任何人簽核。

## Part A｜決策說明（來龍去脈）

### A1. 原先的人工流程（現況）

```
業務 ──(mail / Teams)──▶ 助理 ──▶ 進 ERP 下單 ──▶ BPM 通知主管簽「下單同意」
                                                        │
                                        主管進 BPM 自己翻待辦、簽核
                                                        │
                          助理進 TipTop 打出貨單號 ──▶ 出貨 ──▶ 倉庫撿料
```

**這條流程真實發生過的痛點：**

- **一張單的資料被重複輸入多次** —— 業務打一次給助理，助理再打一次進系統。
- **簽核「卡在誰身上」不知道** —— 主管要自己進 BPM 翻待辦匣，才知道有沒有單要簽。
- **口頭退單沒有軌跡** —— 群組裡一句「麻煩退單、改出貨單備註」講完就沒了，
  誰要求的、為什麼、處理了沒，全靠人記得。
- **承辦收到通知後要自己回系統翻清單** —— 通知只寫名字、不是點了就到那一筆。

### A2. 優化後的流程

```
業務在 GAS 下單頁下單（自動編發包單號、順手帶貨指寄資訊）
        │  Chat @提及 + 深連結
        ▼
主管在 GAS 簽「發包同意」
        │
        ▼                          ┌── BPM 的「下單同意」簽核 ──┐
助理只補 3 個 TipTop 欄位（不重打）   │  副本信 → GAS → Chat @提及  │
        │                          │  主管點連結 → 登入 BPM 原生簽 │
        ▼                          └───────────────────────────┘
倉庫核單（Chat @提及倉庫）
```

全程 Chat **@提及 + 深連結**，通知會「找人」，而不是等人回系統翻。
BPM 那一關的簽核仍在 BPM 完成，我們只是把「你有一張單要簽」這件事**主動推到主管面前**。

### A3. 遇到的問題

BPM 簽核跑在 ERP 內網，GAS 在 Google 雲端，**兩者網路上碰不到彼此**。
結果就是主管得在兩個系統之間切換、還要自己進 BPM 翻待辦，
GAS 這側也看不到「這張單簽核到哪了」。

### A4. 解決方法（不動既有系統）

請 BPM 在**既有的**簽核通知信之外，**多寄一份副本**到一個專用信箱
（例如 `bpm-intake@waferlock.com`）。GAS **只讀**這封副本信、解析、發 Chat 通知。

| 這個做法 | 說明 |
|---|---|
| 不改 BPM 流程 | 只在通知設定多加一個副本收件人 |
| 不改 ERP | 完全不碰 |
| 不動主管的個人信箱 | 不需要轉寄規則、不需要開帳號委派 |
| 簽核仍 100% 在 BPM 原生完成 | GAS 只給連結，主管自己登入 BPM 簽 |

### A5. 帶來的利益

- **減少重複輸入**：業務下單填的資料，助理不必重打，只補 TipTop 產生的 3 個欄位。
- **簽核從「被動翻找」變「主動推送」**：Chat @提及該簽的人，附上直達那一筆的連結。
- **退單有了軌跡**：申請、原因、處理人、處理時間都留下來（已完成）。
- **承辦不必回系統翻清單**：點通知就到那一筆。

**已經驗證的量化成果**（可對外引用）：

- 單筆簽核頁的開頁時間，從實測 **39 秒**降到約 **3 次 API 往返**。
- 下單當下即通知下一棒 —— 補上了原本「料件出貨免簽核、卻沒有任何人被通知」的缺口。

### A6. 這是政府計畫案流程改動的一環

補助計畫本身就**要求流程改動與可回溯性**（例如 KPI 需與 ERP 銷售單據勾稽、
查核點要求以共同識別碼串接領料紀錄與工單）。

因此這件事是**計畫交付的一部分，不是額外的便利性需求**。
做這條整合，是在滿足計畫的查核要求，順帶把日常流程也簡化了。

### A7. 這是 0.5 版，未來可延伸

現在用「讀一封副本信」是**最小、最安全**的起步。
未來廠商建置完整 AI 系統時，可以在這個基礎上，再延伸到 ERP／EasyFlow 的 API
（例如直接讀簽核進度、以本人身分回寫）。

**現在做的 Chat 通知、深連結、人員對照表，屆時都會沿用**，不是拋棄式的東西。
v0.5 是地基，不是繞路。

## Part B｜資安說明

> 這一節專門回答一個問題：**把 BPM 的通知接到 GAS，會不會影響公司資安？**

### B1. 資料怎麼流動

```
BPM ──(既有通知 ＋ 多一份副本)──▶ 專用 Gmail 信箱（公司網域內）
                                        │  GAS 只讀
                                        ▼
                                 解析（單號 / 申請人 / 單別）
                                        │
                                        ▼
                            Chat @提及主管 ＋ BPM 直達連結
                                        │  主管點連結
                                        ▼
                        登入 BPM（用自己的帳密）→ 在 BPM 原生簽核
```

### B2. 為什麼「連到 GAS」不影響公司資安

1. **單向、由內往外**
   GAS **從不主動連進公司內網**。是 BPM 把信推出來、GAS 被動地讀。
   在架構上，GAS 不可能成為「從外面進入公司網路」的入口。

2. **只讀、不寫回**
   GAS 做的事就是：讀一封副本信、解析、發一則 Chat 通知。
   它**不寫入 ERP、不寫入 BPM、不碰任何內部資料庫**。

3. **簽核 100% 在 BPM 原生完成**
   GAS 只提供一個連結。主管點連結、用**自己的帳號密碼**登入 BPM、在 BPM 裡簽。
   GAS **從不代替任何人簽核**，所以 BPM 上那筆簽核紀錄，
   **完全是主管本人在 BPM 產生的、沒有被任何外部系統碰過**——稽核軌跡是真的。

4. **副本信不擴大機密暴露**
   那封通知信本來就已經寄給主管了。我們只是在**同一個公司 Google Workspace 網域內**
   多加一個副本收件人，**沒有創造新資訊，也沒有把任何資料送到組織以外**。
   而且信件內容是「哪張單要簽」的 metadata（單號、申請人工號、單別），
   **不是單據內容、不是金額、不是客戶個資**。

### B3. 可以在哪裡增強資安查核

我們主動列出可加強的控管點，供資安審視：

- **專用信箱權限最小化**：只有 GAS 的服務帳號能讀，**絕不設成「知道連結的任何人」**。
- **副本只針對特定流程／單別**：不是全公司的簽核信都灌進這個信箱。
- **GAS 系統存取限公司 Google 帳號登入**：沿用現有的登入閘門。
- **連結只導到 BPM 登入頁**：連結本身**不含任何憑證**，主管仍需自己登入才能簽。
- **GAS 端不信任信件裡的工號做授權**：身分一律以「BPM 登入後的 session」為準，
  GAS 只把工號用來決定「該 @提及誰」，不用它決定任何權限。
- **專用信箱不轉寄到組織外**。
- **只處理來自 BPM 寄件位址的信**（例如 `tiptop@wfe.com.tw`），其他來源一律忽略。
- **金鑰不硬編碼**：所有金鑰放在 GAS 的 Script Properties，不寫進程式碼（專案既有規範）。

### B4. 一句話總結

> 這個設計的資安邊界，就是「**只讀一封已經存在的通知信、發一則 Chat 提醒**」。
> 它**不新增任何對公司內部系統的寫入或連入路徑**。

## Part C｜技術規格

### C1. 架構與可重用的現有零件

這一版**不重造輪子**，沿用專案裡已經驗證過的機制：

| 要用的東西 | 來源 | 用途 |
|---|---|---|
| 輪詢 + Gmail 標籤模式 | `docs/gas-email-intake.gs` | 用標籤當「不可逆的處理狀態」（`已進件`），避免重複處理 |
| `mentionOf_` / `deepLink_` / `postWarehouseChat_` | `docs/gas-dispatch-approval.gs` | Chat @提及 + 深連結 + 送訊息 |
| `Chat人員對照` 分頁概念 | 既有 | email ↔ Chat UID 對照 |

### C2. 需 IT 配合的事

只有一件：**請 BPM 在簽核通知外，多寄一份副本到專用信箱。**
這是**系統通知設定**，不是帳號權限，風險趨近於零。
細節見 [附錄：給 IT 的問題清單](#附錄給-it-的問題清單)。

### C3. GAS 端解析規則

**信件標題**（實際範例）：

```
(待辦事項) [BPM][簽核通知][axmt410][一般訂單] 單號:W5303-260820002 申請人:WA0202
```

要抽出的欄位：

| 欄位 | 範例 | 來源 |
|---|---|---|
| 事件類型 | 待辦事項 / 簽核完成 / 退件 | 標題開頭（**決定 v0.5 能做到哪，見附錄 B**） |
| 程式代號 | `axmt410` | 標題 |
| 單別 | 一般訂單 | 標題 |
| 單號 | `W5303-260820002` | 標題 |
| 申請人工號 | `WA0202` | 標題 |
| 待簽單直達連結 | `.../PerformWorkFromMail?...&hdnWorkItemOID=...` | 內文，原樣抽出 |

**顯性失敗**：解析不出來的信，要**留紀錄並通知人，不可以靜默跳過**（專案既有規範）。

### C4. 工號對照表

信件裡的身分是**工號**（如 `WA0108`），但 Chat @提及要用 email／Chat UID。
新增（或擴充現有對照表）一份：

| 工號 | email | Chat UID |
|---|---|---|
| WA0108 | someone@waferlock.com | （21 位數字） |

### C5. 接到現有 Chat 通知機制

新增一支輪詢函式（照抄 `gas-email-intake.gs` 的 `pollEmailIntake` 形態）：
掃專用信箱的未處理信 → 解析 → 用 `mentionOf_` 對到人、`deepLink_` 帶連結、
`postWarehouseChat_` 送出 → 貼「已處理」標籤。

觸發器**人工在 Apps Script 後台新增**（專案規範：不自動建立觸發器）。

### C6. 對單

用標題裡的**單號**（`W5303-260820002`）對到 GAS 出貨明細的「訂單編號」欄，
讓 BPM 的簽核與 GAS 的出貨紀錄串得起來。

### C7. 分階段路線

| 版本 | 做什麼 | 依賴 |
|---|---|---|
| **v0.5（本文件）** | 副本信 → 解析 → Chat @提及 + 深連結；主管在 BPM 原生簽 | 只要 BPM 加副本收件人 |
| v1.0 | 讀 BPM 簽核進度（目前卡在誰身上） | 待評估 |
| v2.0（廠商） | ERP／EasyFlow API 整合、以本人身分回寫 | 完整 AI 系統建置時 |

## 附錄｜給 IT 的問題清單

> 這一階段刻意**不問** ERP／WebService 的 API、不問回寫、不問信箱委派——
> 我們只需要「BPM 多寄一份副本信」這一個小設定。

### A. 副本信箱本身

1. BPM 的簽核通知信，除了寄給各直屬主管，能不能**多寄一份到一個專用副本信箱**
   （例如 `bpm-intake@waferlock.com`）？
   *為什麼問*：這是整個方案的入口，我們讀這個副本、不碰任何主管的個人信箱。

2. 副本設定能不能**只針對特定流程／單別**（例如我們要處理的 `axmt410 一般訂單`、發包相關的單），
   而不是全公司所有簽核信都灌進來？
   *為什麼問*：只收要處理的，避免雜訊。

### B. 信會在「什麼時機」寄（這題最關鍵）

3. 這封通知信是**只有「送簽（待辦）」時寄**，還是**簽核完成／退件時也會各寄一封**？
   *為什麼問*：截圖那封是「待辦事項」（通知主管去簽）。但要讓下游動起來，
   我們需要知道「這張單**簽核通過了**」這個事件。若系統只在待辦時寄、通過時不寄，
   那我們就只看得到「誰要簽」、看不到「簽好了沒」——這會決定 v0.5 能做到哪。

4. 若簽核完成時**不會**自動寄信，能不能設定成會寄？
   *為什麼問*：這是備案。若不行，就要改用別的方式判斷通過，成本會上升。

### C. 信的內容穩不穩定（決定程式會不會壞）

5. 這封信的**標題與內文格式是固定的嗎**？例如標題
   `(待辦事項) [BPM][簽核通知][axmt410][一般訂單] 單號:... 申請人:...` 這個結構，
   會不會因為系統更新或設定調整而改變？
   *為什麼問*：我們靠解析這封信抓「單號、申請人、程式代號」。格式一變，程式就靜默失效。

6. 寄件者位址固定是 `tiptop@wfe.com.tw` 嗎？
   *為什麼問*：GAS 要靠寄件者 + 標籤過濾，確認只處理 BPM 的信。

### D. 對照資料（把工號變成人）

7. 能不能提供一份**員工工號對照表**（工號 ↔ 姓名 ↔ email）？
   例如信裡的 `WA0108`、`WA0202`、`WA0261-張郁欣`。
   *為什麼問*：信裡的身分是工號，但我們要 @提及、要對到人。這是一次性的組織資料，不涉及權限。

### E. 順帶確認（跟內部流程有關，不一定是 IT）

8. 標題裡的「單號 `W5303-260820002`」，跟助理在 TipTop 打的**出貨單／訂單編號是同一個號**嗎？
   *為什麼問*：這是把 BPM 簽核對到 GAS 出貨明細的鑰匙。若是同一個號，對單就成立。

## 明確不在本版（v0.5）範圍

- 不呼叫任何 ERP／EasyFlow 的 API（v0.5 只讀信）。
- 不回寫任何東西到 ERP／BPM。
- 不動任何主管的個人信箱（不需要轉寄規則、不需要帳號委派）。
