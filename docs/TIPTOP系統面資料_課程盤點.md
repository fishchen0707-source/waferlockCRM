## 一、下單到出貨的完整鏈路（作業代號）

課程文件證實的實際流程，比我們之前推測的更精確：

```
客戶主檔 axmi250（申請）／axmi221（直接改地址業務代號）
   ↓
訂單 axmt410 ──送簽 EasyFlow──→ 已核准
   │
   ├─ BOM 需求：訂單選鎖類選項 → 送簽核准後系統自動產生 BOM，不必人工建
   │
   ↓
出貨通知單 axmp210（訂單→出通單，寫入 axmt610）
   ↓
出貨單 axmp220（出通單→出貨單，寫入 axmt620）── 送簽 EasyFlow ──→ 倉庫扣帳
   ↓
（一般訂單）直接開發票／應收：axrp310 或「轉應收發票」ICON → axrt300 應收維護 → 發票開立
（工程案／需簽收的客戶）先進在途倉 → 客戶簽收 axmp470 → 產生客戶簽收單 axmt628 → 才開發票
```

**訂單變更**：已核准訂單要改用 `axmt800`（我方資料夾內原本就有這支文件，現在確認用途）。
**訂單結案／取消**：`axmp410`。
**訂單追蹤查詢**（含出貨相關轉單記錄）：`axmq210`。

> ⚠ 這裡有兩個相似代號要分清楚：`axmq210`＝**客戶額度查詢**（工程案文件裡的用法），
> 但主索引文件說訂單追蹤也查 `axmq200`。**兩者哪個是訂單追蹤要跟鼎新當面確認**，
> 課程文件本身在這裡不完全一致。

## 二、🔑 找到「客戶簽收單」的真身——原本標成「5801」的那個

之前的訪談與初版需求書都用「5801」代稱「客戶簽收單」，且標成不確定。
課程文件給出確切答案：

| 我們原本猜的 | 課程文件確認的 |
|---|---|
| 5801 客戶簽收單，代號不確定 | **`axmt628` 客戶簽收單**，由 `axmp470`（客戶簽收單轉單作業）產生 |

**觸發條件**：客戶主檔要先勾選「客戶出貨簽收」（`axmi250` 裡的欄位）。
勾了之後，該客戶的訂單會**自動**帶出這個勾選。

**兩種單別**，對應兩種情境：
- **`C5503` 出貨待簽收** — 一般客戶延遲認列收入的情境
- **`A5506` 工程案-出貨待驗** — 工程案，指定在途倉庫 `1Z0001`

**在客戶簽收之前**，貨已經出了，但：
- 庫存只是移到「在途倉」（`ZZ0005` 或 `1Z0001`），**所有權仍是公司的**
- **不能開發票、不能認列銷貨收入**
- 但客戶的信用額度（`axmq210` 查）**仍然照算**——這筆貨還是占用他的額度

**簽收完成後**，才轉應收帳款（`axrt300`）、開發票。

**查詢報表**：`axmr670`／`axmr690`（簽收狀況）、`axmr620`（出貨明細，不論是否簽收都在此）、
`axmr610`（出貨清單，依單別分）。

> 🎯 **這對我們的意義**：保固認定要串「出貨日、交屋日、安裝日」——
> 對這一批走簽收流程的客戶（工程案、經銷／建商），**`axmt628` 的簽收日期**
> 很可能就是比出貨日更接近「交屋日」的那個時間點，比出貨單日期更適合當保固起算依據。
> 這個要跟鼎新確認：`axmt628` 的簽收日能不能透過 API 拿到。

## 三、庫存「可用量」的真正演算法——這是我們一直標問號的地方

**已確認**：可用量與「訂單備置（booking）」直接相關，不是單純「現有量 − 出貨量」。

- 訂單登打完後可執行「備置」（`axmi611`），把庫存**保留**給這張訂單（需指定倉庫、儲位、數量）
- 保留之後，`aimq102`（動態庫存查詢）會顯示**備置量**，並有「備置明細」icon 可查是哪幾張訂單占用的
- `axmq611` 可依料號查詢備置狀況
- 要釋放保留：`axmi611` 新增單據，選「退備置」

> 🎯 **這回答了 API-2 的關鍵問題**：**可用量 = 現有量 − 備置量（已被訂單保留但未出貨的部分）**。
> 需求書裡「請說明可用量的算法」這題，鼎新的答案應該就是圍繞 `axmi611`／`aimq102` 的備置機制。
> 這件事要在需求書裡明講，逼鼎新確認演算法與我們的理解一致，而不是讓他們自己定義。

## 四、送貨地址——「MISC」機制，回答了 API-1 的❓

原本需求書寫「❓請確認 TIPTOP 出貨單是否有送貨資訊欄位」，課程文件給出部分答案：

- 客戶主檔可建多組地址，**用代碼區分**：`BILL01`（帳單地址）、`SHIP01`（送貨地址）、
  以及像 `0002`（對帳單寄送地址）這種自訂編號
- **一次性、不想存進客戶主檔的送貨地址，可以用「MISC」**，直接在訂單上打

> 🎯 **這解決了大半個問題，但沒有全解決。**
> - 如果客戶自己的工地／倉庫要收貨 → 用客戶主檔既有的 `SHIP01` 就夠
> - 如果是「貨指寄」給**完全不同的第三方**（例如業務指定寄到某鎖店，
>   收件人是那間店的人，跟下單的客戶毫無關係）→ 用 `MISC` 一次性帶入
>
> **需要跟鼎新確認的是**：`MISC` 這個一次性地址（收件人、電話、地址三項）
> 能不能透過 API 讀到。如果 `MISC` 的內容不會出現在出貨單的可查詢欄位裡，
> 那我們現行「貨指寄」還是要靠自己的表單收，回不到 ERP 去。

## 六、客戶主檔裡本來就有的「集團碼」——跟我們的客編分歧問題有關

課程文件：多個客戶編號其實是同一個客戶時，用「集團碼」統一。
例：環電的 `A01372`、`A01372-1`～`A01372-5`，集團碼都填 `A01372`；
信用額度也可以共用（子代號額度設 0，共用母代號的額度）。

> 🎯 這跟我們自己在 CRM 端遇到的「客編兩種格式並存、同一地址寫法不同會拆成兩個客編」
> 是同一類問題的 ERP 版本。TIPTOP 已經有解法（集團碼），但解法本身要靠人工正確歸類，
> 不是自動判斷。**這不影響我們的 API 需求範圍**，但了解這個機制後，
> 若要串「同一個客戶在 CRM 與 ERP 對得起來」，比對鍵應該考慮用集團碼而不是單一客戶編號。

## 七、料號與 BOM 是「訂單時動態產生」的，不是預先建好的目錄

這解釋了為什�公司的料號長得像 `L396-1E17E1-A0122D-A1CA1-2X30A`：

1. 業務／業助建立訂單時，**選鎖類選項**（不是輸入現成料號）
2. 存檔後，系統**自動產生**對應的成品料號與品名
3. 訂單送簽核准後，系統**自動產生 BOM 表**（不用人工建）
4. 分群碼開頭 `W` 的訂單，會 mail 通知生管與研發助理去補齊料號欄位、覆核 BOM

> 🎯 **這代表 API-4「料件主檔」的資料是動態長出來的**，不是一份固定目錄。
> 我們要的介面應該是「**查詢已存在的料號**」而不是「取得完整字典後離線比對」，
> 因為新的料號組合每天都可能因為新訂單而冒出來。這件事應該讓需求書講清楚，
> 避免鼎新以為給我們一份靜態清單就夠了。

另外，一般料件（非訂單動態產生的）建檔走 `aimi100`，
關鍵欄位：庫存單位（SET）、分群碼（`WL3XX`＝美規／`WL7XX`＝歐規）、
來源碼（M＝自製）、狀態碼、ABC 碼、策略碼（2＝MRP）。
**分群碼 `WL3XX`／`WL7XX` 這個美規歐規的分類，之前我們完全不知道**，
可能跟型號後綴的意義有關，值得留著備查。

### 🔴 修正一個上次的推論：BPM ≠ EasyFlow

08-12 的紀錄裡我推論「倉庫口中的 BPM 極可能就是 EasyFlow」，理由是兩者的表單流轉行為很像。
**這批新訓教材明確列出三個是分開的系統**：

| 系統 | 用途 | 瀏覽器限制 |
|---|---|---|
| 鼎新系統（TIPTOP） | 進銷存 | 限用 IE／新版限用 Edge |
| **EasyFlow** | **簽核系統** | 限用 IE |
| **BPM** | **出勤系統**（打卡、請假） | 用 Chrome |

**BPM 官方定義是出勤系統，不是簽核系統。** 這代表兩種可能：
1. 倉庫人員口語習慣把「開啟 EasyFlow 網頁去看今天有哪些單」也叫「BPM」（誤用習慣稱呼）
2. 或者倉庫真正在用的是我們完全沒聽過的第四套東西

**這件事必須直接問倉庫**：「妳說的 BPM，是不是就是 EasyFlow 那個要用 IE 開的簽核系統？」
不要再假設下去。之前需求書沒有把這個推論寫進對外版本（只留在內部版本紀錄），所以不影響已交給鼎新的文件，但**跟鼎新開會時不要沿用這個推論**。
