## 1. 使用本介接的有「兩方」　🔴 請先確認此節

本介接完成後，會有兩個獨立的系統呼叫它：

| 使用方 | 位置 | 用途 |
|---|---|---|
| **A. 我方內部系統** | 公司內部 ／ 雲端 | 出單流程：發包簽核、出貨登錄、倉庫核單、查詢、報表 |
| **B. 外部廠商平台** | **公有雲（Render）** | 政府補助計畫之「顧客 360 資料中台」與 6 個 AI Agent |

> 🔴 **B 方系統部署在公司網路之外的公有雲。**
> 這代表介接**不能只在內網開放**，必須考量對外存取的安全設計。
> 請在方案中明確回覆：

- 對外存取方式：VPN／專線／IP 白名單／API Gateway？
- 驗證機制：API Key／OAuth／憑證？是否支援**依使用方分別發證與分別授權**？
- 兩方的權限可否分開？（例如 B 方只能讀、不能寫；或只能存取部分欄位）
- 可否分別記錄各使用方的呼叫紀錄，供稽核與問題追查？
- 傳輸加密（HTTPS／TLS 版本）與憑證管理由誰負責？

> **權限分離是硬需求**，不是選配。ERP 內含成本、單價、客戶名單，
> 外部廠商平台不應取得超出其功能所需的資料。

## 2. 介接原則

1. **雙向。** 讀取為主，另有三項明確的寫入需求（見第 4 節）。
2. **鬆耦合。** 需以中介層設計，避免與單一供應商綁定，降低日後替換成本。
3. **錯誤要能分辨。** 「查無資料」與「系統錯誤」必須回傳不同代碼，
   **不可一律回空值**——空值會被我方系統當成正常結果，造成靜默的資料落差。
4. **讀寫權限分離。** 讀取與寫入須為不同權限，寫入端點須可獨立停用。
5. **不得影響 ERP 正常作業。** 若即時查詢有效能疑慮，請主動說明並提出替代方案。

## 6. 「即時」的定義（須於合約載明）

計畫書對前台的承諾是「**即時查詢訂單、交期、庫存與出貨狀態**」。
為避免爭議，請於方案中明確載明：

- 「即時」是**同步查詢 ERP**，還是**快取＋定期更新**？

- 尖峰時段的查詢回應時間承諾為何？

> 我方立場：庫存與出貨狀態若只能做到每日同步，
> 則無法取代現行的人工查詢，該介面的效益將大幅降低。

## 9. 驗收條件

請以下列方式驗收，**不以「有回傳資料」為通過標準**。

| 介面 | 驗收方式 |
|---|---|
| API-1 出貨單 | 指定一張**多品項**的實際單據，明細筆數與內容需與 TIPTOP 畫面完全一致 |
| API-2 庫存 | 指定一個**儲位超過 3 個**的料號，需回傳全部儲位 |
| API-2 庫存 | 完成一筆出貨後，庫存數需在**約定秒數內**反映 |
| API-3 訂單 | 指定一張**尚在簽核中**的單據，需能判斷卡在哪一關 |
| API-3 訂單 | 交期需與 ERP 畫面一致 |
| API-4 料件 | 指定一組**僅左右向不同**的料號，品名規格需可分辨 |
| API-5 序號 | 指定一組已出貨序號，需能回推出貨日與出貨單號 |
| API-6 客戶主檔 | 需能分辨建商／經銷商／鎖店／散戶 |
| API-7 銷貨與發票 | 指定一段期間，金額合計需與 ERP 報表一致（KPI 勾稽的前提） |
| API-9 BOM | 指定一個型號，需回傳其維修常用零件 |
| API-10 領料 | 一筆領料寫入共同識別碼後，需能**用該識別碼查回這筆領料** |
| W-1／W-2 | 寫入後於 ERP 畫面可見，且**不影響原單據狀態與後續流程** |
| 權限分離 | 以外部廠商的憑證呼叫時，**取不到成本與單價欄位** |
| 對帳機制 | 連續 3 個工作日產出對帳報表，差異數為 0 或差異可具名列出 |
| 全部 | 查無資料與系統錯誤回傳不同代碼 |
| 全部 | 提供介面文件（WSDL 或等效規格）與測試環境 |
