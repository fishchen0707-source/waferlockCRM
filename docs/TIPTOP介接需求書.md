**我方最想解決的三件事**，請在方案中對應說明：

1. 助理目前需**從 TIPTOP 畫面整段複製出貨品項**貼到我方表單 → 希望由介面取得
2. TIPTOP 畫面的**儲位欄位長度有限，一個料號只顯示得下 2～3 個儲位**，

## 1. 我方系統概述

我方已自行建置一套內部出單流程系統（Google Apps Script ＋ Google 試算表 ＋ Supabase），
目前實際運作中，涵蓋：發包簽核、助理出貨登錄、倉庫核單、查詢、報表。

此系統為我方營運資料的主體，未來將由外部 CRM 廠商來介接。
**本次向貴司申請的介接，是讓我方系統能讀取 TIPTOP 的營運資料，避免同一筆資料重複輸入。**

---

## 2. 介接原則

1. **第一期唯讀。** 不寫入 TIPTOP，不影響現有單據流程、權限與作業習慣。
2. **預留雙向。** 請在介面設計與報價中，一併說明第二期開放寫入的可行性與追加成本。
3. **錯誤要能分辨。** 「查無資料」與「系統錯誤」必須回傳不同的代碼，
   **不可一律回空值**——空值會被我方系統當成正常結果，造成靜默的資料落差。
4. **不得影響 ERP 正常作業。** 若即時查詢有效能疑慮，請主動說明並提出替代方案。

## 3. 介面需求

### API-1　出貨單（含明細品項）

對應作業：`ATMT620`　·　頻率：**每 15～30 分鐘**（或事件觸發）

| # | 欄位 | 必要性 | 備註 |
|---|---|:--:|---|
| 1 | 出貨單號 | 必要 | |
| 2 | 單別 | 必要 | 例：5501／5506，請提供正式定義與狀態碼對照 |
| 3 | 出貨日期 | 必要 | |
| 4 | 單據狀態 | 必要 | 含是否已核（核單後狀態變更） |
| 5 | 對應訂單編號 | 必要 | 我方用來串回訂單 |
| 6 | 客戶編號、客戶名稱 | 必要 | |
| 7 | **明細**：料號、品名、數量、單位 | **必要** | 一張單多筆，需完整回傳 |
| 8 | 明細：批號、儲位 | 希望 | |
| 9 | **送貨資訊：收件人、電話、地址** | **待確認** | 見下方 ❓ |
| 10 | 發票別 | 希望 | |
| 11 | 備註 | 希望 | |

> ❓ **請確認 TIPTOP 出貨單是否有「送貨資訊」欄位。**
> 我方目前的送貨對象（收件人／電話／地址）常與客戶主檔的地址不同，
> 且該資訊目前不存在於任何系統中。若 ERP 無此欄位，我方將自行於前端收集，
> 但需要先確認，才能決定我方表單的欄位設計。

---

### API-2　即時庫存（含儲位、批號、可用量）　🔴 **優先度最高**

對應作業：`AIMQ102`（動態庫存查詢）、`AIMI100`（料件基本資料）、`aimi201`（倉庫儲位資料）
頻率：**即時**

| # | 欄位 | 必要性 | 備註 |
|---|---|:--:|---|
| 1 | 料號 | 必要 | |
| 2 | 倉別 | 必要 | |
| 3 | **儲位（完整清單）** | **必要** | 🔴 見下方說明 |
| 4 | 批號 | 必要 | 同料號不同批號需分別呈現 |
| 5 | 入庫日 | 希望 | |
| 6 | 現有量 | 必要 | |
| 7 | **可用量** | **必要** | 請說明算法：是否已扣除已配未出、在途 |
| 8 | 虛擬倉旗標 | 希望 | 我方需排除已出貨的帳上倉（代號「1」開頭者） |

> 🔴 **本項的關鍵規格：介面必須回傳該料號的全部儲位，不得沿用畫面的顯示上限。**
>
> 現況是 TIPTOP 畫面的儲位欄位長度有限，一個料號只顯示得下 2～3 個；
> 超過的部分看不到，倉儲人員因此必須另外維護一份外部清單，
> 而那份清單不會同步回 ERP。結果是**全公司最準的儲位與可用量資料不在 ERP 裡**，
> 其他單位查到的庫存是不準的。
>
> **如果介面沿用同樣的顯示限制，這個問題不會被解決，這支介面對我方就沒有價值。**
> 請在方案中明確回覆此項是否做得到。

---

### API-3　訂單（含狀態）

對應作業：`axmt410`（一般訂單維護）、`axmq001`（訂單狀態查詢）
頻率：**每 15～30 分鐘**

| # | 欄位 | 必要性 |
|---|---|:--:|
| 1 | 訂單編號、單別、訂單日期 | 必要 |
| 2 | 客戶編號、客戶名稱 | 必要 |
| 3 | 業務人員 | 必要 |
| 4 | 明細：料號、品名、數量、單位、單價 | 必要 |
| 5 | 單據狀態（未確認／已確認／已出貨／結案等） | 必要 |
| 6 | 預計交期 | 希望 |

**另需：簽核進度。** 我方理解簽核流程在 EasyFlow（EFGP）而非 TIPTOP，
所需資訊為：**目前在哪一關、由誰待簽、已簽核者與時間、是否曾退回**。

> 我方目前的實際困擾是「單據卡在誰身上不知道」，
> 只取得「已核准／未核准」的結果並不足夠。
> 若 EasyFlow 既有方法（如 `GetApproveLog`、`GetFormInfo`）即可滿足，
> 請直接告知，我方不需要另行開發。

---

| 1 | 料號 | 必要 | |
| 2 | 品名、規格 | 必要 | |
| 3 | 單位 | 必要 | |
| 4 | 產品別／分類 | 希望 | |

## 4. 需釐清事項（請於報價前回覆）

### 版本與現況

1. 我方 TIPTOP 版本（GP 版次）與 EasyFlow（EFGP）版本？
2. `azzi700`（整合服務基本資料維護）目前已註冊哪些服務？**有無現成可直接使用者？**
3. TIPTOP 的「標準 WebService」是**現成可呼叫的介面**，
   還是需逐支以 4GL 開發後註冊？**計價方式是以介面支數計，還是以人天計？**
4. 我方已購買／已啟用哪些整合相關模組？

### 技術可行性

5. 出貨單是否有送貨資訊（收件人／電話／地址）欄位？能否帶出？（見 API-1）
6. 庫存介面能否回傳**完整儲位清單**，不受畫面欄位長度限制？（見 API-2，最關鍵）
7. 可用量的計算邏輯為何？是否已扣除已配未出、在途？
8. 單別 5501／5506／5801 的正式定義與狀態碼對照表
9. 倉庫端使用的簽核系統是否即 EasyFlow？能否提供簽核進度查詢？

### 工程與維運

10. 是否提供**測試環境**與測試帳號，供我方自行驗證？
11. 錯誤處理設計：查無資料與系統錯誤如何區分？
12. 呼叫頻率上限？即時庫存查詢是否會影響 ERP 正常作業效能？
13. ERP 日後升版時，介面的相容性與維護責任如何界定？
14. **第二期雙向寫入**的可行性、限制與概估成本（本期不執行，先了解）

## 5. 驗收條件

請以下列方式驗收，**不以「有回傳資料」為通過標準**。

| 介面 | 驗收方式 |
|---|---|
| API-1 出貨單 | 指定一張**多品項**的實際單據，回傳明細筆數與內容需與 TIPTOP 畫面完全一致 |
| API-2 庫存 | 指定一個**儲位超過 3 個**的料號，需回傳全部儲位 |
| API-2 庫存 | 完成一筆出貨後，庫存數需在約定時間內反映（「即時」的定義請以秒數載明） |
| API-3 訂單 | 指定一張**尚在簽核中**的單據，需能判斷目前卡在哪一關 |
| API-4 料件 | 指定一組**僅左右向不同**的料號，品名規格需可分辨 |
| 全部 | 查無資料與系統錯誤回傳不同代碼 |
| 全部 | 提供介面文件（WSDL 或等效規格）與測試環境 |
