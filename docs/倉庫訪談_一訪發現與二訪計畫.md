> 一訪日期 2026-08-12，約 58 分鐘，受訪者為倉儲主管。
> 逐字稿見 [`倉庫訪談_逐字稿_20260812.txt`](倉庫訪談_逐字稿_20260812.txt)。

> **結論先講：倉庫比預期複雜不是因為問得不夠，是因為它本來就不是「一個流程」。**

## 一、五個假設，四個被推翻

| 我原本的假設 | 實際情況 | 影響 |
|---|---|---|
| 倉庫是一個地方 | **8 個倉**，各有獨立負責人（號碼與名稱的對應只確認了 3 個，見附錄） | 核單頁的「倉庫」概念要重新定義 |
| 出貨是一條流程 | **三個科各走不同流程**：一科成品＋E-Home 門口機／二科公務（弱電）／三科飯店系統＋機器人。受訪者原話「它走的又不一樣」 | 我們做的只涵蓋一科的一部分 |
| **主要痛點是撿錯料** | **最花時間的是「印單」**。受訪者原話：「我曾經花了一個上午就在印發票」 | 🔴 方向要修正，見第二節 |
| 手機優先是對的 | 對，但**紙本不能省**——「稽核要查驗紙本」（ISO 要求） | 手機是輔助，不是取代 |
| 序號只是記錄 | 現在記的是**生產批號**（為維修追溯），與保固序號是不是同一件事**還沒問清楚** | 待二訪釐清 |

唯一沒被推翻的：撿錯料確實會發生（料號太長、只看前後沒看完整），但**不是主要痛點**。

## 二、🔴 最重要的發現：我們幫不到最痛的那一段

**印單流程（受訪者說最花時間）**：

```
BPM 看單 → 下載 → 複製單號 → 確認派送（兩次點擊）
  → 跳 TipTop ATMT620（出貨單）→ 查詢貼單號 → 確定
  → 5501 直接變「可」／5506 要再按一次確認
  → 印單（機器慢、畫面卡）→ 選印表機 → 列印 → 等 → 關掉視窗
  → 若需發票 → 再開發票 → 又約 4 個步驟
```

受訪者對 TipTop 的評語：「**它一直要按確認、確認、確認，它沒有辦法一件化**」。

**這一段我們碰不到**——它在 BPM 與 TipTop 內部，而 EasyFlow 授權未談成。

### 但有三件我們做得到的事，能減少它的痛

1. **讓單更早進來。** 業助丟單越來越晚（以前 8:30，現在拖到 10~11 點），
   導致全部集中在下午 3:30 前趕完。而「忘記送簽」也會讓倉庫看到 Teams 訊息卻查不到單。
   → 我們的簽核進度透明化正好解這個：業助看得到卡在哪、主管看得到待核。
2. **取代 Teams 的查詢。** 受訪者主動說：「我們有時候想要用單號直接查詢，
   可是 Teams 查詢很不容易，我們就要用滑的去找它」。
   → 這正是查詢頁的價值，而且是**倉庫自己說出來的需求**，不是我們猜的。
3. **發票電子檔。** 見第四節，這是受訪者自己提出的改善願望。

**要誠實面對的**：我們做的五頁，對倉庫的價值主要在「**取代 Teams 的通知與查詢**」，
而不是取代他們的核心工作。使用者在訪談中也是這樣定位的（「不是為了取代 BPM，
只是為了先取代 Teams」），倉庫的回應是「可以」。這個定位是對的，但要清楚說出來，
否則會誤以為做了五頁就解決了倉庫的問題。

## 三、🔴 最該優先處理的一件事：那份 Excel

受訪者透露的最關鍵事實：

- TipTop 的儲位欄位**字數有限，只能顯示 2~3 個儲位，第 4 個就看不到**
- 所以倉儲人員**自己維護一份 Excel**（放 Google 雲端），記詳細儲位、批號、入庫日
- **這份 Excel 不會同步到 TipTop 的動態庫存**
- 助理看的是 TipTop 動態庫存（**所以助理看到的庫存不準**）
- 「因為我們就是沒有辦法看到說這個儲位還有多少台」
- 每天要把出貨單一一手動扣除

**而且**：

> 維護者 8/10 起休養，**這份表從 8/10 之後就沒有更新**，他 8/31 才回來。
> 回來後要花兩三天才補得完。

這是**單點故障**（bus factor = 1）：全公司最準的成品儲位與可用量資料，
只存在一個人的 Excel 裡，而那個人不在。
（8/10 起停更、8/31 回來，**約三週**。逐字稿裡的「兩個月」是他上一次車禍休養的時間，不是這次。）

→ **這件事的優先度高於我們做的任何一頁。** 它已經是 Google Sheet，
所以技術上最好處理（不必轉檔、不必匯入），難的是流程：誰維護、怎麼避免再回到一個人身上。

## 四、受訪者自己提出的改善願望（優先做這些）

使用者自己提的需求，接受度最高、阻力最小：

### 1. 發票改給電子檔，業助自己印自己寄

現況的問題（受訪者原話整理）：
- 印好後「有的交業助、有的要電子檔」，**紙本印了才發現對方要電子檔 → 白印**
- **只有倉庫能抓發票電子檔**，業助拿不到，所以一定要經過倉庫
- 曾發生貨與發票同箱，**師傅把整箱抱走，會計沒收到發票**
- 有客戶要求兩天內寄掛號，「每天寄一封掛號」，受訪者認為該集中或改 Email
- 業助給錯／不完整地址，**發票一直被退回**
- 寄錯發票（因為單上沒有單價，且價格不統一）

→ 我們能做的：**核單完成後上傳發票 PDF，業助自己下載。** 使用者在訪談中已提出，
受訪者回應「這也是一個」。這是投報率最高的一項，因為它同時解掉白印、寄錯、退回三個問題。

⚠ 但二聯式一定要印（感熱紙），這部分省不掉。

### 2. 貨運單的訂單編號

- 大榮／新竹的系統**只有倉庫能下載**
- 貨運號碼由物流系統自動帶出
- 訂單編號**目前沒有 key，但可以 key**，受訪者說「沒差啊，其實還好」（因為本來就在複製姓名電話）

→ 有了訂單編號，託運單就能自動對回出貨單，助理不必再問倉庫。
**這解掉了 `shipment-worker` 配對困難的根因**，而且成本是「多貼一次」。

### 3. 平板 ＋ 螢幕

受訪者提到 Johnny 前年就提過條碼＋平板，但「工程浩大、沒人處理」而擱置。
她想要的是「平板可以馬上知道庫存有多少、位置在哪裡」——**就是第三節那份 Excel 帶著走**。

## 五、二訪的策略：不要再從頭問一遍

一訪已經把「一科成品出貨」問得相當完整。二訪應該換做法：

### 做法 A：畫流程圖給她確認（強烈建議）

把一訪的內容畫成流程圖，用「**我理解得對不對？**」取代「請你再講一次」。
她只要指出錯的地方，比重新敘述省時十倍，而且會自然補出漏掉的分支。

### 做法 B：其他科、其他倉分開約，不要混

二科（弱電）、三科（飯店／機器人）、以及成品倉以外的各倉是**不同的人、不同的流程**。
混在一場問，答案會互相污染。

### 做法 C：分辨哪些適合用文字問

| 適合文字（是非題／確認題） | 必須面對面（流程／為什麼／要看實物） |
|---|---|
| 5801 客戶簽收單是什麼？ | 二科／三科的出貨流程 |
| 各倉號碼與名稱怎麼對？4005 存在嗎？ | 換貨／RMA 走哪個倉、什麼流程 |
| 產品上有條碼嗎？外箱上有嗎？ | 包裝實際怎麼做、誰在包 |
| 生產批號與保固序號是同一組數字嗎？ | 那份 Excel 的實際結構（要等 8/31） |
| 併箱多常見？ | 出貨檢驗實際怎麼檢 |
| 簽回的單收在哪？有沒有追蹤？ | 讓她操作我們的核單頁 |

## 七、一訪得到的硬約束（設計時不能違反）

這些是系統設計必須遵守的事實，不是待確認事項：

1. **發票號碼與出貨單日期連動。** 一旦開立 13 號的發票，12 號的就開不了。
   → 所以倉庫**不接受預開明天的單**。任何「提前處理」的功能都會踩到這條。
2. **時間規則**：業助丟單截止 13:30；大榮 14:00 收、新竹 15:30~16:00 收；
   15:30 前必須完成所有出貨；16:00 後才能丟隔天的單；16:00 後倉庫做入庫。
   → 通知時機要配合這個節奏，不能全天即時轟炸。
3. **紙本不能省**（ISO 稽核要查驗）。
4. **BPM 未完成，TipTop 什麼都不能做。** 順序是硬的。
5. **5501／5506 的差別**：5501 已收款、需開發票；5506 工程案、先出貨後請款、
   不開發票，另走 5801 客戶簽收單請款。
6. **同料號不同批號必須分儲位**（維修追溯用），業助可能指定批號出貨。
7. **標準品分北／中／南區各自庫存**，同料號但案名不同，不可互相挪用（要調貨）。
8. **月底最後一天不出貨**——會計要關帳，倉儲人員當天核庫存。
   原話：「每個月底我們都會關帳嘛，最後一天，會計會關帳，所以最後一天是不出貨」。
   → 任何排程、催辦、每日通知都要跳過這一天。
