# 師傅端流程盤點 — 從「通知師傅」往回推，缺了哪些環節

> 2026-08-14　·　純流程盤點，不談系統架構
> 標記：**✅ 已有**（做好且在用）／**🟡 部分**／**🔴 缺**／**❓ 不確定**（沒問過，不推測）

---

## 先講結論

以「LINE 通知師傅 → 師傅查出貨進度」為終點往回推，
**最大的缺口不在通知，也不在查詢，而在這三處**：

1. 🔴 **師傅名冊不存在** — 沒有名冊就沒有 uid，通知寄不出去。這是第 0 步。
2. 🔴 **沒有人確認「貨到師傅手上了」** — 貨是寄給師傅／鎖店，不是客戶。
   沒有簽收這一步，師傅排安裝日期等於在猜。
3. 🔴 **現場缺件／錯件沒有回報路徑** — 撿錯料是已知會發生的事，
   但目前只有月底對帳才會發現，師傅站在現場時無路可走。

## 四、到貨　🔴 **這一段整段是空的**

| # | 流程 | 狀態 | 說明 |
|---|---|:--:|---|
| 3-1 | **預計到貨日通知師傅** | 🔴 缺 | 大榮／新竹出貨後 1～2 天到。**這個資訊目前沒人給師傅** |
| 3-2 | **師傅簽收確認** | 🔴 缺 | 貨是寄到師傅／鎖店。**沒有任何人在系統上確認「收到了」** |
| 3-3 | **件數核對** | 🔴 缺 | 倉庫說「業助不知道件數，只能大概估」。師傅收到幾件、對不對，沒人核 |
| 3-4 | **貨到才可排安裝** | 🔴 缺 | 現在師傅可以先排日期，貨沒到就白跑 |
| 3-5 | 貨運異常（延誤、遺失、破損） | 🔴 缺 | 誰發現、誰處理、怎麼補 |

> **這一段是「師傅查出貨進度」真正想解決的事。**
> 師傅要問的不是「出貨單號是多少」，是「**我的料到了沒、幾件、什麼時候能裝**」。

## 九、通知這件事本身

> 「用 LINE uid 通知師傅」不是一個動作，是一組流程。

| # | 流程 | 狀態 | 說明 |
|---|---|:--:|---|
| 8-1 | 推播送出 | ✅ 已有 | 已實測送達 |
| 8-2 | **送達失敗的處理** | 🔴 缺 | 師傅換手機、封鎖、解除綁定 → **誰知道？** |
| 8-3 | **已讀／未回應的追蹤** | 🔴 缺 | 發了沒人看，案子就卡在那裡 |
| 8-4 | **接單確認** | ✅ 已有 | |
| 8-5 | **群組 vs 個人** | 🔴 缺 | 現在貼師傅 LINE 群，**群裡每個人都看得到客戶姓名電話地址**——這是個資問題 |
| 8-6 | **通知時機** | 🟡 部分 | 倉庫有明確節奏（13:30 截單／14:00 大榮／15:30 新竹／**月底最後一天不出貨**），通知不能全天轟炸 |

## 十、我認為最該先補的五個（依「不補就會出事」排序）

| 順序 | 缺口 | 為什麼是它 |
|:--:|---|---|
| 1 | **師傅名冊 ＋ LINE 綁定** | 這是第 0 步。沒有它，「通知師傅」整件事不存在 |
| 2 | **師傅簽收（到貨確認）** | 沒有它，師傅排安裝在猜，白跑的成本由師傅和客戶一起承擔 |
| 3 | **現場缺件回報 → 補件** | 撿錯料是**已知會發生**的事，卻沒有處理路徑 |
| 4 | **群組通知改個人通知** | 客戶姓名電話地址現在攤在群組裡給所有師傅看，這是個資風險 |
| 5 | **預計到貨日給師傅看** | 成本最低、感受最直接：出貨日 + 1～2 天，資料已經有了 |
