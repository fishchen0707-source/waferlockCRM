# 獨立報表程式設計規格

> 狀態：**已實作，尚未部署**。2026-08-10。
> 程式：[`gas-dispatch-report.gs`](gas-dispatch-report.gs)　驗證：`scripts/verify-dispatch-report.js`（140 項全過）
> 待辦：新建 Apps Script 專案貼上、啟用 Sheets 進階服務、設 `REPORT_SINCE`、部署後跑 `checkReportSetup()`。
> 現有的 ⑥ 報表頁（在 `gas-dispatch-approval.gs` 內）維持不動，作為輕量的待辦看板；
> 本文件描述的是另一支專責報表的 Apps Script。

---

## 為什麼要另開一支程式

使用者的理由是「加在原本這邊會太厚重」（`gas-dispatch-approval.gs` 已 4000+ 行、90 個函式）。
這個擔心成立，但**檔案大小不是最好的理由**——設計文件當初判斷「一個專案、多個頁面」的論據
仍然有效：讀表邏輯是整套系統最脆弱、改最多次的部分，拆開就有兩份拷貝，
下次冒出新欄名漏改的那一份**不會報錯，只會安靜地少讀一個欄位**。

真正該拆的理由是這三個，都由 2026-08-10 的實測暴露：

### ① 兩者的讀取需求相反

現有程式處處在**減少**讀取量（只讀到最後一筆有效單號、只讀用得到的欄、快取待辦清單），
目的是「開頁要快」。報表要的正好相反：**全量、含歷史、可跨年比較**。
硬塞進同一支程式會變成兩套互相拉扯的需求。

### ② 資料稽核不該混進出單流程

實測出現「某承包商工資合計 112 億」（622 筆平均 1800 萬／筆）與
「待出貨最舊 942 天」。要查清楚需要「列出所有異常值、指出在哪個分頁哪一列」——
那是稽核工具的職責。

### ③ 報表適合 `batchGet`，出單流程不適合

先前否決 Advanced Sheets Service 的理由是「日期變序列數字要自行轉換，
而部分分頁的日期是手打文字（`3/28`，無年份），轉錯會漏單」。
那個風險在出單流程很嚴重（漏一張單就是漏一筆錢），但**報表可以承受**：
轉不出來的日期歸到「日期不明」並顯示筆數，比安靜漏掉誠實。
而 `batchGet` 對全量掃描的效益遠大於現在（一次往返讀完 17 個分頁）。

## 已確認的決策（2026-08-10）

### 1. 時間基準：兩種都要，可切換

| 基準 | 來源 | 用途 |
|---|---|---|
| 出貨日 | 出貨明細的「出貨日期」 | 銀貨兩訖，算營收。**未鍵出貨單號的不計入** |
| 發包申請日 | 業務分頁的「發包申請日期」 | 看業務接單節奏 |

同一份報表提供切換。兩套彙總都要實作——接單旺季與出貨旺季可能不同月。

### 2. 歷史資料：設起算日，之前不統計

指令碼屬性 `REPORT_SINCE`（`YYYY-MM-DD`，例 `2026-01-01`）。
- 未設定時**必須明確警告**，不可默默統計全部（那就會出現 942 天那種數字）
- 頁面上要標明「統計範圍自 X 起」，否則主管會以為是全部歷史
- 這是刻意犧牲跨年比較換取數字可信——等舊資料清乾淨再放寬

### 3. 工資：要能對照累計請款防超額

**這是最重要的一組，也是設計文件標為「會出錯付錢的地方」的那一項。**

比對每一列的「報價單數量」（或「合約數量」）與「累計請款數量」，
列出 `累計 > 報價` 的案，含分頁、列號、單號、承包商、差額。

- 兩個欄名都有別名（`報價單數量`／`合約數量`、`累計請款數量`），沿用現有別名表
- 欄位缺一個就無法比對 → 該分頁列為「無法檢查」並具名，**不可靜默略過**
- 這一區要放在報表最前面：它是唯一會直接造成金錢損失的項目

## 顯示內容

| 區塊 | 內容 |
|---|---|
| 🔴 超額請款警示 | 累計 > 報價的案。放最前面 |
| 業務銷售額 | 依業務代碼，筆數／售價／毛利，可切時間基準 |
| 通路銷售額 | 依「案名／購買通路」分組（MOMO／蝦皮／官網／散戶／其他） |
| 外包師傅工資 | 依承包商，筆數／工資合計／月分組 |
| 時間間距分析 | 下單→簽核、簽核→出貨、出貨→倉庫核單 的平均與最久 |
| 資料稽核 | 金額極端值、日期無法解析的筆數、承包商名稱不一致、未收錄的業務代碼 |

「時間間距」需要各階段的時間戳：簽核欄含時間、出貨明細有登錄時間與出貨日期、
倉庫核單有核單時間。**簽核欄是文字**（`✅ 核准 email 2026-08-06 09:12`），
要用正則取出時間，取不到就歸入「無法計算」並計數。

## 與現有程式的關係

**共用契約，不共用程式碼。** 新程式唯讀，自己實作讀表（`batchGet`），
但欄名常數與別名表從 `gas-dispatch-approval.gs` **複製一份並在檔頭註明來源與複製日期**。

看似違反 DRY，但：
- 兩支是不同的 Apps Script 專案，GAS 本來就沒有 import
- 唯讀程式讀錯欄位的後果是「報表數字不對」，不是「寫壞資料」

真正的防護是**用檢查取代共用**：新程式要有一支 `checkFieldParity()`，
把它認得的欄名清單與實際表頭比對，發現「實際存在但它不認得」的欄名就警告。
這與結構快取那輪的原則一致——**會變動的事實寫成可執行的檢查，不要寫進文件**。

⚠ 新程式**唯讀**：不可有任何 `setValue`／`appendRow`。
它讀的是同一份正式資料，寫入權限一律留在出單那支。

## 實作順序建議

1. `batchGet` 讀表 ＋ `checkFieldParity()`（地基，先確認讀得對）
2. 🔴 超額請款警示（價值最高、邏輯最單純）
3. 資料稽核（先把 112 億與 942 天那類異常查清楚，否則後面的數字都不能信）
4. 業務／通路／工資三組彙總 ＋ 時間基準切換
5. 時間間距分析（最複雜，要從簽核文字解析時間）

**第 3 項做完就該回頭確認第 2、4 項的數字是否合理**，不要一路做完才驗。

## 驗證要求

沿用 `scripts/verify-dispatch-approval.js` 的模式（GAS stub ＋ 真實表頭）另建
`scripts/verify-dispatch-report.js`。必須涵蓋：

- `REPORT_SINCE` 未設定時要警告；設定後起算日之前的資料確實被排除
- 兩種時間基準各自的彙總正確，且**跨年同月不可合併**（2025-12 vs 2026-12）
- 超額請款：`累計 > 報價` 抓得到；欄位缺失的分頁列為「無法檢查」而非略過
- 日期無法解析（手打 `3/28`）歸入「日期不明」並計數，不可靜默丟棄
- 金額為空／非數字／極端值不可讓合計變 `NaN`
- `checkFieldParity()` 能抓出「實際表頭有、新程式不認得」的欄名
- **全檔不得出現 `setValue`／`appendRow`**（唯讀保證，用字串搜尋斷言）

## 實作時補的三個決定（2026-08-10）

規格沒寫、但不決定就寫不下去的三處。都寫在程式註解裡，這裡留紀錄：

### ① 切換基準只換「分組用的日期」，不換金額來源

規格說兩個基準來自不同分頁（出貨明細／業務分頁）。若照字面各算各的，
兩邊的金額欄不同（售價 vs 承包總價），數字沒有可比性，切換就失去意義。

改成：**金額來源固定**，基準只決定每一筆掛在哪個月——
出貨明細的列用發包單號回查申請日、業務分頁的列用發包單號回查出貨日。
查不到的（約一半出貨沒有發包單號）歸「日期不明」並顯示筆數，不靜默丟棄。

### ② 超額請款不受 `REPORT_SINCE` 限制

起算日的目的是讓統計數字可信；但多付出去的錢沒有時效。
舊單超額了現在才發現，錢一樣已經付了。所以這一區一律全量檢查，頁面上有註明。

### ③ 毛利只算「有進價」的列

進價空白時若當 0，毛利會等於售價，看起來像賺翻了。
改成不計入，並顯示「毛利（N 筆）」與稽核區的「無進價 N 筆」，
讓人看得出這個毛利是用多少筆算出來的。
