# 0800 語音客服技術棧（對外分享版）

> 一套**不買話務系統、不架 SIP**，純用 Web 技術與雲端 AI 服務拼出來的
> 客服語音方案，已實測跑通（真人通話、錄音、逐字稿、摘要、AI 語音接聽）。
> 已移除公司識別資訊、金鑰與網址；適合想在既有客服系統上加語音能力的團隊參考。

---

## 0. 全景圖

```
                        ┌─────────────────────────────────┐
   顧客手機瀏覽器        │        值機桌面（客服端網頁）      │
   （LINE 導流開網頁）    │  screen-pop 反查客戶｜ACW 紀錄    │
        │               └────────────┬────────────────────┘
        │    ①真人通話線               │
        ├──── WebRTC P2P 語音 ────────┤
        │（信令：Supabase Realtime）   │
        │（TURN：Cloudflare 時效憑證）  │
        │                            │
        │    ②AI 語音線（顧客先接 AI，要真人再轉）
        ├──── WebSocket ── Python Voicebot（ASR→LLM→TTS）
        │         或
        └──── 直連 Gemini Live API（native audio，短效 token）

   掛斷後 ③錄音處理線：
   混錄音檔 ─→ Python STT Worker ─→ Storage 存檔
                    │ NVIDIA Riva ASR（zh-TW 逐字稿）
                    │ LLM 產一句摘要
                    └→ 寫回客服系統對話串（「🎙️ 通話錄音｜摘要…」）
```

三條線可獨立採用：只要真人通話（①＋③）、只要 AI 接聽（②）、或全套。

## 1. 真人通話線（WebRTC）

### 組件

| 組件 | 技術 | 角色 |
|------|------|------|
| 通話客戶端 | 原生 WebRTC API（無框架，vanilla JS 一支 client 共用） | 客服頁與顧客頁共用；`role: agent/customer` |
| 信令 | **Supabase Realtime broadcast ＋ presence** | 免自架信令伺服器！SDP/ICE 走 broadcast，上下線探測走 presence |
| NAT 穿透 | STUN（Google 公用）＋ **Cloudflare Realtime TURN** | TURN 憑證由 Edge Function 以 API 換發**時效憑證**（TTL 86400），前端拿不到長期金鑰 |
| 備援信令 | Node（Express＋ws）自架版 | 同一套協定（join/offer/answer/ice/bye），部署 Render/Fly 即用；Realtime 版上線後作備援 |

### 設計要點

- **只有 agent 發 offer**（主叫），customer 回 answer——避免雙方同時發 offer 的 glare 問題。
- ICE candidate 在 remoteDescription 就緒前先進 pending 佇列，避免亂序丟包。
- **通話錄音在瀏覽器端混音**：Web Audio API 把本地＋遠端兩路 stream 接進同一個
  `MediaStreamDestination`，MediaRecorder 錄成 webm；同步降採樣一份 16kHz 單聲道 wav
  給後續 STT（模型吃 wav 比 webm 省事）。
- **無人接聽逾時**（約 50 秒）→ 呼叫「待回電」API：把 房號/姓名/電話 落成一則
  特殊訊息（`type: callback_request`）進客服收件匣，值機桌面看得到、可回撥。

### 為什麼不用 SIP/話機

顧客從即時通訊（LINE 等）導流過來，點連結就能通話——瀏覽器即話機。
省掉話務系統授權與 SIP trunk，代價是「顧客得在網頁裡」，適合以線上導流為主的場景。

## 2. AI 語音接聽線（兩代做法）

### 2a. 自建 Voicebot（pipeline 式）

```
瀏覽器麥克風 ──16k PCM──▶ FastAPI WebSocket
                             │
                   ┌─────────┼──────────┐
                   ▼         ▼          ▼
              Riva ASR    LLM 對話    Riva TTS
              (串流辨識)  (短句人設)   (合成語音)
                   └─────────┴──────────┘
                             │
瀏覽器喇叭 ◀──合成音訊────────┘
```

| 環節 | 選型 | 重點 |
|------|------|------|
| ASR | **NVIDIA Riva `parakeet-ctc-0.6b-zh-tw`**（build.nvidia.com 雲端） | 走 **gRPC**——Deno/Edge Function 打不了 gRPC，這是必須另立 Python 服務的原因 |
| LLM | NVIDIA NIM 上的 OpenAI 相容端點 | **即時對話用小模型**（如 llama-3.1-8b），大推理模型延遲撐不起語音；回答限 30 字內、口語化 |
| TTS | Riva TTS | 注意：**中文 TTS 多只支援 zh-CN 腔**，臺灣華語腔目前缺；選型時先試聽 |
| 轉真人 | LLM 人設內建 `[TRANSFER]` 標記 | 偵測到標記就把通話升級成第 1 節的真人 WebRTC |
| 併發模型 | ASR gRPC 串流跑在背景執行緒＋queue，與 asyncio WebSocket 橋接 | 避免阻塞事件圈 |

### 2b. Gemini Live API 直連（現行版）

- 前端直連 **Gemini Live WebSocket（native audio）**：麥克風 16k PCM 上行、
  AI 24k PCM 下行，**barge-in（插話打斷）由模型原生處理**——pipeline 自建版最難做好的就是這個。
- **金鑰不進前端**：Edge Function 先用 server 端金鑰換一張**短效 ephemeral token**，
  model／音色／system prompt 全部鎖在 token 的 `liveConnectConstraints`，
  前端拿到的 token 只能開這一種對話。
- LLM function calling 接工具端點（查工單進度、口頭報修建單）：
  工具由另一支 Edge Function 實作，**確定性邏輯（查表、狀態碼轉中文）寫死在程式，
  不交給模型**——模型只負責對話與決定何時呼叫工具。

### 兩代取捨

| | 自建 pipeline | Gemini Live 直連 |
|--|--------------|------------------|
| 延遲/插話 | 自己調，barge-in 難做 | 原生處理，體驗好 |
| 腔調 | TTS 腔調受限 | 音色選擇多 |
| 成本結構 | 按各服務分開計費，可換件 | 綁單一供應商 |
| 可控性 | 每一環可替換（ASR/LLM/TTS 各自獨立） | 黑盒較多 |

建議：**先用託管式（2b）驗證商業價值，保留 2a 作為成本優化與去綁定的退路**。

## 3. 錄音處理線（STT Worker）

```
掛斷 → 前端 multipart 上傳（webm 完整錄音 ＋ wav 16k 單聲道）
      → Python FastAPI Worker（部署 Render/Railway/Fly 任一 PaaS）
         1) webm 存 Supabase Storage（私有 bucket）
         2) wav → Riva gRPC → zh-TW 逐字稿
         3) 逐字稿 → LLM →「40 字內摘要＋分辨客服/顧客的分行逐字稿」
         4) 原子 append 一則訊息回對話串：
            「🎙️ 通話錄音（3分12秒）｜摘要：…｜含逐字稿」
```

要點：

- **為什麼是獨立 Python 服務**：唯一原因是 gRPC。若改用 REST 型 STT
  （Whisper API 等），這層可以併回 Edge Function。
- 摘要 prompt 要求輸出 JSON（`responseSchema` 鎖格式）：`{transcript, summary}`，
  transcript 每句標「客服：／顧客：」。
- STT/LLM 失敗**不擋主流程**——錄音照存，逐字稿欄位留空，回應帶 `asr_err/llm_err`
  除錯欄位（顯性失敗，方便排錯）。
- 摘要訊息寫回對話串走**原子 append RPC**（`msgs = msgs || new`），
  與其他寫入方（webhook、客服端）並行不互撞。

## 4. 值機桌面（客服端）

- 來電 **screen-pop**：以來電號碼即時反查客戶主檔（電話→候選客戶列表，
  因電話非唯一鍵，同號多戶時列出讓客服選），彈出客戶 360 面板。
- **ACW（After-Call Work）結構化落地**：通話結束強制填分類＋摘要，
  落成對話串裡一則 `type: acw` 訊息（含通話秒數、分類、座席），
  之後客服績效報表（通話量/平均時長/分類分佈）直接從這些結構化訊息統計，
  不需要另建報表資料表。
- 通話紀錄與文字客服同一個收件匣（platform=phone 的對話串），
  客戶的 LINE 訊息、通話錄音、ACW 在同一條時間軸上。

## 6. 踩坑清單

1. **Edge Function（Deno）打不了 gRPC**——需要 gRPC 的 AI 服務（Riva）就得另立
   Python/Node 常駐服務，架構上一開始就要留這個位置。
2. **中文 TTS 腔調**：多數雲端 TTS 中文只有 zh-CN 腔，對臺灣使用者體感明顯，
   選型先試聽再定案。
3. **即時語音別用大模型**：推理型大模型首 token 延遲就毀掉對話感；
   8B 級小模型＋30 字內短句人設，體感遠勝。
4. **錄音双軌（webm＋wav）在前端就準備好**：後端免轉檔，STT 直接吃 16k wav。
5. **信令用 Supabase Realtime 是個甜點**：省一台信令伺服器，但要處理
   presence 事件與 broadcast 的順序問題（ICE 先到先暫存）。
6. **TURN 別省**：同 NAT 測試都會通，跨網路（行動網路↔家用寬頻）沒 TURN 就是斷；
   用 Cloudflare 按量計費的時效憑證，前端永遠拿不到主金鑰。
7. **待回電要落地成資料**，不是只彈通知——值機桌面重整後還在、可指派、可追蹤。
