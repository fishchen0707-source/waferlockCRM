# 倉庫訪談清單

> 2026-08-11 訪談用。問題按「答案會不會改變已寫好的程式」排序，不是按重要性。
> 每題都註明**為什麼問**——訪談時間有限，知道答案要拿來幹什麼才問得下去。

---

## A. 會推翻已寫好的程式（優先問完這五題）

### A1. 撿料時遇到的問題有幾種？

現在的倉庫核單頁只有兩顆按鈕：**已撿料完成** / **有問題**。

**為什麼問**：如果實際上常見的是「缺料」「料號不符」「數量不對」「品項有但包裝破損」
這些不同情況，各自的後續處理不一樣（缺料要等進貨、料號不符要業務改單），
那只給一個「有問題」就等於把分類工作丟回給讀訊息的人。

→ 請他們列出**最近一個月實際遇到的狀況**，不要問「可能會有什麼問題」（那會得到想像的答案）。

### A2. 回報「有問題」之後，那張單接下來怎麼走？

現在的程式：狀態寫「有問題」→ **該筆從待核清單消失**，通知助理與業務。

**為什麼問**：這假設了「有人會去處理，處理完重新開一張」。如果實際上是
「倉庫先擋著、助理補料或改單、然後倉庫再核一次」，那我做錯了——
它應該要能**回到待核狀態**，否則單子會憑空消失，沒有人知道它卡在哪。

→ 問：問題解決之後，是同一張單繼續，還是重開一張？

### A3. 一張出貨單會不會分兩次送？

現在的資料模型：出貨明細**一列 = 一次出貨**，倉庫核單一次就終結。

**為什麼問**：如果「料先寄一部分、剩下等進貨」很常見，那一列裝不下兩次核單記錄。
這跟當初「一次發包可能對到多次出貨」是同一類問題，而那個問題我們用
「出貨明細獨立一張表」解掉了——分批出貨可能需要同樣的處理。

### A4. 倉庫有幾個人？會不會兩個人同時在核同一批？

**為什麼問**：程式有並發保護（同一筆被兩人同時核，後按的會看到「已經處理過了」）。
但如果他們的習慣是「兩個人分頭撿同一張單的不同品項」，那並發保護會變成互相擋，
需要改成分項核單。

### A5. 撿料的人是專職倉管，還是師傅兼？

**為什麼問**：如果是師傅兼，那「倉庫」和「承包商」是同一群人，
`DISPATCH_WAREHOUSE` 名單與承包商對照表會重疊，而未來的 LINE 群組通知也會撞在一起
（你先前說「可能會有重疊」，這題就是要確認到什麼程度）。

## B. 會影響下一階段設計

### B1. 🔴 貨運公司與託運單號是誰產生的、記在哪？

**這是我認為最大的缺口。** 出貨明細目前**完全沒有**「貨運公司」與「託運單號」欄位。

**為什麼問**：專案已經有 `shipment-worker` 在做託運單解析與配對，而那件事
一直配對困難（設計文件說根因是「貨指寄只存在 Teams」）。如果倉庫是託運單號的
產生者，那它應該在倉庫核單那一步就進系統——現在卻是事後才想辦法配對回來。

→ 具體問：叫貨運是誰打電話／上系統？託運單號抄在哪？黑貓、新竹、宅配通還是自己送？
　同一天多張單會不會併成一張託運單？

### B2. 怎麼知道有沒有料？

**為什麼問**：如果「有問題」最常見的原因就是沒料，那真正該解的是
「業務下單時就看得到庫存」，而不是等到撿料才發現。
但那需要 TipTop 的庫存資料，而 TipTop 無法串接（EasyFlow 授權洽談中）。
先確認痛點有多大，再決定值不值得做人工的庫存表。

→ 問：TipTop 上的庫存數字準嗎？你們會不會自己另外記一份？

### B3. 一天出貨幾次？有截單時間嗎？

**為什麼問**：現在助理鍵完單就立刻推 Chat 通知倉庫。如果倉庫其實是
「每天下午三點統一撿料出貨」，那即時通知只是製造干擾，
應該改成**批次彙總通知**（例如每天 14:00 推一次當日待撿清單）。

### B4. 需要紙本撿料單嗎？

**為什麼問**：手機優先的設計假設他們邊看手機邊撿。如果實際上是印出來、
在紙上打勾、最後才回系統輸入，那手機頁面的價值大減，
該做的是「一鍵列印當日撿料清單」。

## C. 補齊既有的空白（時間夠再問）

### C1. `W5501` / `W5506` 這些單別是什麼意思？

設計文件列為待確認、標記「現階段不阻塞」。已知是 TipTop 單別
（一般訂單／工程案訂單／雜項收入訂單…）。
**為什麼問**：報表若要依單別分類統計會需要，現在只是照實記錄。

### C2. 現在是怎麼收到出貨通知的？

**為什麼問**：驗證我們的假設。如果他們現在是看 Teams、而 Teams 訊息本來就
沒人固定看，那「改成 Chat 通知」的價值要重新評估——
可能真正的問題是通知管道，不是內容。

### C3. 倉庫核單完成之後，那則「備存訊息」你們會用到嗎？

**為什麼問**：我們設計「核單完成推完整出貨資訊到 Chat」是為了取代 Teams 備存。
但如果倉庫從來不回頭查那些訊息，那則訊息的讀者其實是助理或業務——
那格式應該照**他們**的需求設計，不是照倉庫的。

## D. 從實際出貨訊息看到的（2026-08-11 補，優先度等同 A 類）

看了五個群組的真實訊息（`出貨-台北出貨`、`台中成品出貨` 等）後補的。
這些**不是猜測，是訊息裡真的出現的東西**，而系統完全沒有涵蓋。

### D1. 🔴 發票是兩個維度，我做成一個欄位

現在只有「發票別」一欄（出貨待驗無發票／電子發票／二聯／三聯）。但實際訊息裡：

| 發票**種類** | 發票**寄送方式** |
|---|---|
| 無發票 | 貨及發票寄同一處 |
| 出貨待驗無發票 | **發票貼外箱**（`【貨+出貨單+發票(貼外箱)】`）|
| 電子發票／二聯／三聯 | **電子檔給指定人**（`發票電子檔To Phoenix`、`【發票】PDF TO R`）|
| | 與貨分開寄（不同地址）|

**種類和寄送方式是獨立的兩件事。** 塞進一個欄位，填的人一定二選一而漏掉另一半。

→ 問：這兩件事是不是總是一起決定？發票寄錯或漏寄的情況多嗎？
　「電子檔 To 某人」那個「某人」是固定的還是每次不同？

### D2. 🔴 產品序號要回報，系統完全沒有這個資料

- 「**請提供連號流水號**」（吉廷營造 L372*7 組）
- 「**尾數號碼TO YAPIN**」

倉庫撿料時要記下產品序號並回報給指定的人。這是**保固追溯的關鍵**
（公司本來就有保固登錄系統），而它現在只存在 Teams 訊息裡——
跟「貨指寄」一模一樣的問題：關鍵資訊沒進任何系統。

→ 問：序號是每台都要記，還是只記起訖（連號）？記在哪？誰會回頭查？
　保固登錄那邊拿得到這個序號嗎，還是各記一份？

### D3. 出貨地點不只一個

訊息裡出現「**中科出貨**」「**台北出貨**」「**台中成品出貨**」，而且是**不同群組**。

**為什麼重要**：現在的設計假設「倉庫」是一個地方、一份 `DISPATCH_WAREHOUSE` 名單、
一個 Chat webhook。如果實際上是三個地點各自撿料，那核單頁要能分地點，
通知也要送到對的群組——這跟 LINE 群組對應是同一類問題。

→ 問：一張出貨單會不會需要兩個地點各出一部分？地點是怎麼決定的（就近／庫存在哪）？

### D4. 併箱與分箱的要求

- 「**可寄同一箱，但需分一期/二期**」（兩張出貨單，同一箱）
- 「**希望另包一箱**」
- 「寄二件」「寄1件」← 件數本身就是資訊

**為什麼重要**：現在的模型是一列＝一次出貨，沒有「箱」的概念。
如果併箱很常見，那託運單號會對應到多張出貨單（B1 那題的延伸）。

### D5. 簽回要求

「**請收到貨後 簽回。FAX：04-24622352**」

→ 問：多少比例的單要簽回？簽回的紙本現在收在哪？有沒有追蹤誰還沒簽回？
　（這是應收帳款的憑證，沒簽回可能收不到錢）

### D6. 調撥與內部轉運

- 「此貨從『**2601_石墨黑(77-91)北區標準品**』調入」← 從別的案的料調過來
- 「貨 寄：台北公司 Phoenix 收」← 先寄到自己公司，不是客人

**為什麼重要**：這兩種情況下「貨指寄」不是最終目的地，
而報表若把它當客戶地址統計會失真。也影響託運單配對。

### D7. 出貨單上要加註的文字

- 「**請幫我備註案名**，謝謝」
- 「請在 **2 張出貨單上**備註」

→ 問：這些備註是打在 TipTop 的出貨單上，還是手寫？漏了會怎樣？

### D8. 同日多件的編號與缺出貨單號

訊息用「8/7-1」「8/7-2」「8/7-3」編號，而且**其中兩筆沒有出貨單號**、只有第三筆有
（`W5501-260806021`）。

→ 問：沒有出貨單號的那些是什麼情況（樣品？補寄？客戶自運）？
　那些要不要進系統？（現在的出貨明細以出貨單號為唯一鍵，沒有單號會卡住）

### D9. 貨運公司

訊息裡明確出現「**大榮貨運**」，還有「客戶寄件」（客戶自己叫車？）。
這是 B1 那題的實例——請務必問到底有幾家、怎麼選。

## 訪談時的注意事項

- **問實際發生的事，不要問「你覺得應該怎樣」。** 「上週有沒有遇到撿不出料的？那次怎麼處理？」
  比「你希望系統怎麼做」得到的資訊可靠得多。
- **請他們現場操作一次給你看**（用手機開倉庫核單頁）。看他們卡在哪，比問他們卡在哪準。
- **問「最花時間的是什麼」**，那通常不是我們以為的那件事。
- 目前 ④ 倉庫核單頁**還沒實機驗證過**，訪談時順便讓他們試用，一次收兩種回饋。

## 訪談後要回來更新的

- 若 A2 的答案是「同一張單繼續」→ 倉庫核單要能回到待核狀態（改程式）
- 若 A3 的答案是「常分批」→ 出貨明細的資料模型要調整（改結構，成本高，要先確認頻率）
- 若 B1 有明確答案 → 出貨明細加「貨運公司」「託運單號」兩欄，並接上 `shipment-worker`
- 若 B3 是批次作業 → 通知改成每日彙總，`notifyWarehouse_()` 要改
- **若 D1 確認 → 發票拆成兩欄**（種類／寄送方式），出貨明細加一欄
- **若 D2 確認 → 出貨明細加「產品序號」欄**，並確認能否與保固登錄共用
- 若 D3 確認多地點 → 倉庫核單要分地點，`DISPATCH_WAREHOUSE` 與 webhook 要分組
- 若 D8 的無單號情況常見 → 出貨明細的唯一鍵要重新設計（現在依賴出貨單號）
- 所有答案都補進 [`訂單出貨總表_設計.md`](訂單出貨總表_設計.md) 的「尚未確認」那一節

## 一句話總結這批訊息告訴我們的事

前面五頁做的是「把 Teams 訊息搬進系統」，但這些訊息顯示**真正的資訊量比我們建的欄位多得多**
——序號、發票寄法、併箱、簽回、調撥、多地點。

所以訪談的核心問題其實只有一個：

> **這些訊息裡的每一項，漏掉哪一項會出事？**

會出事的才需要欄位。不會出事的就讓它留在備註欄，不要為了完整而把表做成沒人想填的樣子。
（助理出貨頁那輪的教訓：欄位一多，人就會跳過。）
