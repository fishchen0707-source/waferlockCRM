# 訂單出貨總表 — 三頁設計規格

從「工資發包申請單」擴充成涵蓋**訂單 → 發包 → 簽核 → 出貨 → 倉庫**的單一總表，
各角色透過專屬網頁填寫，不直接面對 40 欄的試算表。

---

## 為什麼要改

**① 名字把範圍講死了。** 現在叫「工資發包申請單」。助理手上拿著一筆弱電料件出貨、
沒有師傅、沒有工資，第一反應必然是「這跟我這筆無關」——**不是偷懶，是表名的問題**。
實際上約有一半的出貨沒有發包單，那一半現在只存在 Teams。

> 🔧 **第一件事就是改表名**（例如「訂單出貨總表」），把「發包」從名字裡拿掉。
> 這步不用寫任何程式，但決定了大家覺得什麼該進來。

**② 發包應該是欄位，不是表。** 訂單／發包／出貨的共同欄位佔一半以上：

| 欄位 | 訂單 | 發包 | 出貨 |
|---|:--:|:--:|:--:|
| 日期、客戶、案名、業務 | ✓ | ✓ | ✓ |
| 型號／品項、數量 | ✓ | ✓ | ✓ |
| 承包商、工資報價、承包總價 | | ✓ | |
| 簽核（副主管／主管） | | ✓ | |
| 出貨單號、貨指寄、發票別 | | | ✓ |
| 訂單編號、請購單號 | ✓ | | |

不發包的單，那組欄位留空——**留空是正常狀態，不是漏填**。

**③ 一列 40 欄，人填不下去。** 所以改用網頁分角色顯示，每個人只看到自己要填的。
網頁解決的是「寬」，不是「資料量」——這點不要混淆。

---

## 架構決策

### 留在 Apps Script + Google Sheets
**理由是身分驗證，不是 Chat。** Chat webhook 只是一個 HTTPS POST，任何地方都打得到
（Supabase Edge Function 現在就在打 LINE）。

真正的理由是 `Session.getActiveUser().getEmail()` ——
Apps Script 免費送一個**不可偽造的 Google 帳號身分**，零設定。
這是整套簽核的地基；沒有它，「主管核准」只是一個誰都能按的按鈕。

### 一個專案、多個頁面，不是三個專案
讀表邏輯（表頭偵測、別名對照、全形正規化、多分頁掃描）是**最脆弱、改最多次**的部分
——光欄名就遇過 4 種格式，別名修過三輪。

拆成三個專案就有三份拷貝，下次冒出新欄名要記得三處都改，**漏改的那個不會報錯，
只會安靜地少讀一個欄位**。

角色判定也必須統一在一處。兩層簽核那輪學到：判定散在兩處就會出現
「畫面看不到但 API 呼叫得動」的漏洞。

### 一列的粒度：維持現況不動
**一列 = 一次發包／請款／出貨**（現行工資發包申請單就是這個粒度，
有「本次請款數量／累計請款數量」可證）。

不改粒度是刻意的——改粒度會動到既有資料與累計邏輯，風險遠大於收益。

### 資料量：用歷史表並存，不要刪
- ❌ 不要「搬走再刪」。**累計請款數量是跨期的**，歷史資料一斷，
  防超額請款的機制就失效——這是會出錯付錢的地方。
- ✅ 當期表 + 歷史表並存，查詢頁同時讀兩張。歷史表只讀不寫、很少查。

| 欄位 | 來源 | 說明 |
|---|---|---|
| 發包申請日期 | 系統帶今天 | |

| **單別** | **人選（必填）** | `發包安裝` / `料件出貨`　← 決定後面流程 |
| 客戶 | 填 | |
| 案名／購買通路 | 填 | 現況混用（散戶／MOMO／蝦皮／官網訂單／實際案名） |
| 型號 | 填 | 簡稱即可（L396、D310），完整料號由助理在出貨階段補 |
| 報價單數量 | 填 | |
| 工資報價(對客戶) | 填 | |
| 承包商 | 填 | **僅發包安裝** |
| 承包報價(組) | 填 | **僅發包安裝** |
| 承包總價 | 填 | **僅發包安裝** |
| 補充說明 | 填 | |
| 發包人員 | 系統帶登入者 | |

**自動編號取代人工填寫**：`Johnson Wu → JW`（名+姓）但 `sammi lin → LS`（姓+名），
且 `SL`(sean lin) 與 `LS`(sammi lin) 只差順序、是兩個不同的人。
人工填遲早會錯，代碼對照走「人員代碼」分頁。

**送出後**：
- 單別＝發包安裝 → 簽核欄留空 → 進主管簽核佇列
- 單別＝料件出貨 → **直接進助理出貨佇列**（不經簽核，2026-08-07 確認）

**料件出貨怎麼繞過簽核又進得了出貨清單**：簽核欄寫入
`✅ 免簽核（料件出貨） <email> <時間>`。待核清單看「簽核欄非空」就排除，
助理的待出貨清單用 `isApproved_()`（只認 ✅ 開頭）納入——兩邊的判定都不必改，
而文字明講免簽核，不會被誤讀成主管核准過。

**寫進業務自己的分頁，不另開新表**。理由是本文件〈資料量〉那節：
累計請款數量是跨期的，新單若進別的表就和該業務的歷史單分家，防超額請款會失效。

**填「報價單數量」不是「本次請款數量」**。下單時還沒請款，
寫進請款欄會讓累計請款從第一天就算錯。部分分頁此欄名為「合約數量」，靠別名處理。

**需要對照表新增「發包分頁」欄**：代碼→分頁無法可靠推導
（`JW → 零售-Johnson` 看得出來，但「一課-eli」「一課-sin」「一課-sam」是暱稱，
猜錯就是把單寫到別人的表上）。執行 `suggestSheetMapping()` 產生建議，人工確認後填入。

|---|---|---|

| 出貨單號 | TipTop | `W55xx-YYMMDDnnn` |
| 出貨日期 | 填 | |

| 貨指寄－收件人 | 填 | 例「宇泰鎖印 李建男」 |
| 貨指寄－電話 | 填 | |
| 貨指寄－地址 | 填 | |

**誠實說明**：這一步不是自動化，是把「手打整段訊息貼 Teams」換成「填欄位＋貼品項」。
工作量持平，換到的是資料進了可查詢的地方、通知自動發到對的群組、倉庫核單有狀態可追。

## ⑤ 查詢頁（已完成）

單一關鍵字查發包單號／出貨單號／訂單編號／客戶／案名／型號／承包商／發包人員／
客人姓名／客人電話／通路訂單編號。唯讀，全員可用。

發包單與出貨明細以**發包單號**串起來顯示（一筆發包可能對到多次出貨）。
**沒有發包單號的出貨也查得到**（弱電料件、鎖胚、建案整批，約占一半）。

**🔴 進價在伺服器端就移除**，只有副主管／主管拿得到。查詢頁是全員可用的，
若只在畫面上藏起來，改一下前端就看得到——敏感欄位的過濾必須發生在資料離開伺服器之前。

**刻意不快取**：查詢條件千變萬化，命中率低，而全量索引會超過 CacheService 的 100KB 上限。
查詢是主動行為，等幾秒可以接受——比自己翻 17 個分頁快得多。
結果由前端非同步取得，開頁本身不查（多數人開這頁是為了查特定一筆）。

**上限 50 筆**並標記已截斷。查詢頁不是用來一次看完全部的。

歷史表並存的部分尚未實作（目前只有當期表）。

## 權限與受保護範圍

**目標狀態：整張試算表受保護，只有 GAS 寫得進去，人一律走網頁。**
這比現在「一組一組加保護範圍」乾淨得多，而且不會有人不小心改到別人的欄位。

| 角色 | 可寫欄位 |
|---|---|
| 業務／工務 | ① 的欄位，且僅限自己建立、尚未簽核的列 |
| 副主管／主管 | 簽核欄（已實作） |
| 助理 | ③ 的欄位 |
| 倉庫 | ④ 的欄位 |
| 全員 | 查詢頁唯讀 |

角色名單沿用指令碼屬性的做法（`DISPATCH_*_APPROVERS` 已有，另加業務／助理／倉庫）。

> ⚠ **導入期的取捨**：要業務改用網頁下單，是三個角色裡阻力最大的。
> 可以先讓業務繼續直接編輯試算表，只把簽核／出貨／倉庫三段上網頁；
> 等前面順了再收。**但這樣就不能整張表上鎖**，權限只能一組一組加。

## 建議的導入順序

一次要三個角色同時改習慣，失敗率很高。照痛感與影響人數排：

| 順序 | 做什麼 | 影響 |
|---|---|---|
| 0 | **改表名**、建「人員代碼」分頁、助理試填一天 | 不用寫程式 |
| 1 | ③ 助理出貨頁 ＋ 通知倉庫 | 助理 1~2 人 |
| 2 | ④ 倉庫核單頁 ＋ 備存訊息 | 倉庫 |
| 3 | ⑤ 查詢頁 | 全員（純加值，無阻力） |
| 4 | ① 業務下單頁、取代 email | 業務（最多人、阻力最大） |

每段跑順再往下，任何一段卡住都還能退回原本做法。

## 🔴 修訂（2026-08-07）：① 的欄位遠比原規格多，且 ①/③ 分工要換

### 怎麼發現的

看到一張**業務實際發給助理的下單訊息**（Vivi Huang，含發包單號 `VH-260803-01`）。
它有五段，而原規格的 ① 只涵蓋最後一段的一小部分。

原規格假設「出貨品項／貨指寄／發票別是助理從 TipTop 抄回來的」，所以放在 ③。
**那是錯的**——那些是業務提供的，助理是拿業務給的資訊去鍵 TipTop，
再把 TipTop 產生的單號抄回來。照原規格做，等於要助理重打一遍業務已經寫好的東西，
而「一筆訂單被輸入六次」正是這整件事要解決的問題。

### 新的分工

| 頁面 | 負責填 |
|---|---|
| ① 業務下單 | 業務知道的**全部**：發包資訊 ＋ 出貨項目 ＋ 送貨資料 ＋ 發票別 ＋ 客人資料 ＋ 售價/進價 |
| ③ 助理出貨 | **自動帶出業務填的內容**，只補 TipTop 產生的：訂單編號、出貨單號、出貨日期 |
| ④ 倉庫核單 | 不變 |

### ① 送出後寫**兩張表**

| 寫哪裡 | 寫什麼 | 為什麼 |
|---|---|---|
| 業務自己的分頁 | 發包單號、日期、客戶、案名、型號、報價單數量、承包商、承包總價、工資報價、發包人員、補充說明 | 主管簽核與**累計請款**都靠這張；累計是跨期的，不能分家 |
| 出貨明細 | 出貨項目、送貨資料、發票別、客人資料、售價/進價（出貨單號**留空**） | 業務分頁沒有這些欄，而在 17 個分頁各加 7 欄是已判斷不可行的事 |

兩張表用**發包單號**串起來。料件出貨沒有發包單號時，出貨明細那列仍成立

## 補充（2026-08-10）：下拉選單與報表頁

### 「選單」分頁

四個常用欄位（案名／購買通路、型號、工項、承包商）改下拉，選項放「選單」分頁，
橫向排列、一欄一個欄位、靠表頭文字定位。都附「其他」，選到時改文字輸入。

**改試算表就會連動，不必重新部署**——GAS 是伺服器端渲染，`doGet` 每次開頁都讀這張表。
選項刻意不快取，換到「改了立刻生效」。

沒建這張分頁時四個欄位退回純文字輸入（現況行為），不會壞頁。

### ⑥ 報表頁：整頁限主管

報表的本質就是彙總金額，「本月毛利」一旦顯示等於把進價反推出來——
**遮欄位在報表上沒有意義**，所以整頁限制。這與 ⑤ 查詢頁（全員可用、只遮進價欄）
是刻意的不同處理。

報表順便當資料品質檢查：疑似同一承包商的不同寫法、對照表沒收錄的業務代碼。
只提示、不自動合併。

### 師傅通知的現況

**一鍵複製**（助理鍵完單即出現通知全文與複製按鈕）。LINE 自動推播暫緩，
卡在 `groupId`：取得它必須有能接 LINE webhook 的 endpoint，
而一個 channel 只能設一個 webhook URL。要做就得開一個獨立的官方帳號。

缺聯絡人與地址時**不產生通知**——半套的通知比不給更糟。
