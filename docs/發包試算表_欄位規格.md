# 工資發包申請單 — 欄位規格與導入設定

搭配 [`gas-dispatch-approval.gs`](gas-dispatch-approval.gs)（簽核網頁）與
[`gas-dispatch-notify.gs`](gas-dispatch-notify.gs)（Chat 通知＋每日備份）使用。

**本階段只做「主管簽核」。** 出貨回填、倉庫核單、品項通知屬階段三，欄位先預留但暫不啟用。

---

## 一、為什麼要做這件事

現行試算表同時是發包單、請款單、簽核表、對帳表，衍生四個問題：

| 現況 | 問題 |
|---|---|
| 「已請款用黃色標示」 | 顏色無法查詢、排序、稽核，複製貼上會掉 |
| O 欄「主管 KEY 英文名 押日期」 | 誰都能打任何名字任何日期，簽核沒有效力 |
| 「每週五業助會定期畫面截錄，以免不小心刪除」 | 截圖看得到卻救不回來 |
| 「各案場分次安裝，請合算累計數量，以免超量請款」 | 防超額付款完全靠人腦 |

本階段解掉前三項。第四項（累計數量自動算）屬階段二。

## 二、欄位定義

### 現有欄位（A–N）不動

| 欄 | 名稱 | 寫入者 |
|---|---|---|
| A | 發包申請日期 | 人 |
| B | 發包單號 | 人（階段二改自動編號） |
| C | 承包商 | 人 |
| D | 客戶 | 人 |
| E | 案名 | 人 |
| F | 型號 | 人 |
| G | 報價單數量 | 人 |
| H | 本次請款數量 | 人 |
| I | 累計請款數量 | 人（階段二改自動計算） |
| J | 工資報價(對客戶) | 人 |
| K | 承包報價(組) | 人 |
| L | 承包總價 | 人 |
| M | 發包人員 | 人 |
| N | 補充說明 | 人 |

> ⚠ **上表是「零售-Johnson」的欄位順序，不是全表通則。**
> 實際盤點 18 個分頁後發現有 4 種格式並存：欄位順序、欄名、甚至簽核關卡數都不同。
> 程式一律以**表頭文字**比對，所以順序不同不影響運作；但凡是按欄位代號做的事
> （最重要的是「受保護範圍」）都必須逐頁確認。詳見第三節。

### 簽核欄：改為系統寫入

| 建議欄名 | 寫入者 | 說明 |
|---|---|---|
| **主管簽核** | **僅 GAS** | 舊欄名有三種寫法，見下 |
| **副主管簽核** | **僅 GAS** | 只有 8 個分頁有這一關 |

改名不是必要的——程式認得所有舊欄名（別名相容）。但**建議統一改名**，
讓大家一眼看出這欄已經不是手打欄位。

程式認得的舊欄名（少任何一個，對應分頁就會被整頁略過）：

| 概念 | 實際存在的寫法 |
|---|---|
| 主管簽核 | `主管簽核`／`主管KEY英文名押日期`／`主管確認/押日期` |
| 副主管簽核 | `副主管簽核`／`副主管KEY英文名押日期`／`副主管確認/押日期` |
| 金額 | `承包總價`／`發包合計` |
| 數量 | `本次請款數量`／`請款數量` |

> 別名比對只做「去空白」，不做模糊比對——這是刻意的：
> 「副主管KEY英文名押日期」若被模糊比對成「主管KEY英文名押日期」，
> 副主管那一關就會被當成主管關寫掉，是最嚴重的一種錯。

### 兩層簽核（8 個分頁）

`一課-eli`／`一課-Jun`／`一課-sam`／`一課-sin`／`一課-BILL`／`三課-Kevin`／
`吳垂容(信益)`／`潘筱凡(金宏)` 這 8 個分頁有「副主管 → 主管」兩關。

流程與判定規則：

| 目前狀態 | 這筆卡在 | 顯示在 |
|---|---|---|
| 兩欄都空 | 副主管 | 「副主管待核」區 |
| 副主管已核、主管空 | 主管 | 「主管待核」區 |
| 副主管**退回** | 終結 | 不再出現（不往上送）|
| 主管已填（不論副主管欄） | 終結 | 不再出現 |

> 最後一條是刻意的：舊資料裡有「主管已手打簽核、但副主管欄從沒填過」的列。
> 若先看副主管欄，這些已完成的單會被倒退回副主管待核。
>
> 「退回」只認 `❌` 開頭（本系統寫入的格式），不用關鍵字比對「退回」二字——
> 舊資料是人工手打，備註裡若剛好出現「退回」會被誤判成已終結，是靜默的資料損失。

寫入格式：

```
✅ 核准 boss@waferlock.com 2026-08-07 14:30
❌ 退回 boss@waferlock.com 2026-08-07 14:30｜型號寫錯，D310 應為 D311
```

email 取自 Google 登入帳號，**無法偽造**。

### 新增欄位

| 欄 | 名稱 | 寫入者 | 階段 | 說明 |
|---|---|---|---|---|
| P | 案件狀態 | GAS/人 | **一** | 取代黃色標示，見下方狀態值 |
| Q | 出貨單號 | 助理 | 三 | TipTop 出貨單號，如 `W5501-260807005` |
| R | 出貨日期 | 助理 | 三 | |
| S | 貨指寄 | 助理 | 三 | 收貨鎖店，如「宇泰鎖印 李建男」 |
| T | 倉庫核單狀態 | 僅 GAS | 三 | |
| U | 倉庫核單人 | 僅 GAS | 三 | |
| V | 倉庫核單時間 | 僅 GAS | 三 | |
| W | 倉庫問題說明 | 僅 GAS | 三 | |

> **S 欄「貨指寄」值得特別注意。** 這個資訊（貨要送到哪家鎖店）目前只存在
> Teams 訊息裡，沒有進任何系統——這正是先前託運單自動配對困難的根本原因。
> 階段三填進來之後，`shipment-worker` 的配對就能從地址模糊比對升級為精確比對。

### P 欄 案件狀態值

```
先寄未裝 → 裝潢中 → 已安裝待請款 → 已核准 → 已請款 → 已付款
                                    ↘ 已退回
```

- `先寄未裝`／`裝潢中`：對應現行表格最上面那幾列（B 欄寫「先寄門廠/宇泰」那些）。
  **實際流程不是線性的**，貨可能先寄、之後才發包，這兩個狀態就是給這種情況用的。
- `已核准`／`已退回`：由簽核網頁自動寫入。
- 其餘由人維護。

### 自動建立的分頁：簽核紀錄

第一次有人簽核時，GAS 會自動建立「簽核紀錄」分頁：

| 時間 | 操作者 | 發包單號 | 動作 | 說明 | 分頁 | 列號 |
|---|---|---|---|---|---|---|

O 欄只留**最後狀態**，這張表留**完整歷程**。不要手動編輯或刪除它。

## 三、🔒 受保護範圍設定（**最重要的一步**）

**不做這步，整套簽核就沒有意義。** 只把手打改成按鈕、但欄位還是人人可編輯，
任何人照樣能竄改簽核結果，只是看起來比較正式而已。

### 🚨 不能一律鎖 O 欄

18 個分頁的欄位順序**各不相同**，同一個欄位代號在不同分頁是不同東西。
實際觀察到的例子：同樣鎖 O 欄，在 `零售-Sammi` 剛好鎖到主管簽核欄，
在 `一課-eli` 鎖到的是**本期請款合計**（業務從此填不進金額），
在 `一課-漢神` 鎖到**補充說明**，在 `陳俊行` 鎖到**出貨沖轉單號**。
而那些簽核欄在 P 的分頁，主管簽核欄**反而沒鎖到**。

**本文件刻意不列欄位代號對照表。** 曾經列過，一天之內就過期兩次——
新增一個「案件狀態」欄，整排欄位就往右移，表上的代號全部失效。
一張過期的對照表比沒有更危險：照著設會鎖錯，而且看起來像做完了。

### 正確做法：用 `checkProtections()` 查，不要用眼睛核對

在 Apps Script 編輯器執行 **`checkProtections()`**（唯讀，不會改任何設定）。
它會逐頁列出：簽核欄有沒有被保護、有沒有鎖到不該鎖的欄，並在最後具名列出未保護的分頁。

依它的輸出逐頁補設：

1. 選取該分頁的簽核欄（副主管欄＋主管欄，有案件狀態欄的一起選；整欄）
2. 右鍵 → **保護範圍**（或功能表：資料 → 保護工作表和範圍）
3. 說明填「簽核欄（僅系統寫入）」→ **設定權限**
4. 選「**只有您**可以編輯此範圍」
5. 重跑 `checkProtections()` 確認變成 ✅
6. 階段三啟用時，再對出貨／倉庫核單相關欄重複

> 💡 連續幾欄（如「案件狀態＋副主管＋主管」剛好相鄰）可以一次選取整段保護，
> 例如 `R:T`。這比逐欄設定少犯錯。

> ⚠ 這裡的「您」必須是**執行 GAS 的那個帳號**（也就是建立 Apps Script 專案的人）。
> Web App 部署成「以擁有者身分執行」，所以它有權寫入；其他人沒有。

> 💡 程式端是用**表頭文字**找欄位，不看欄位代號，所以欄位順序不一致不影響運作。
> 只有「受保護範圍」是試算表本身的功能，必須按實際位置設定——這是唯一會被欄位
> 位置影響的環節，也是唯一需要 `checkProtections()` 的原因。

**`checkProtections()` 的已知限制**：以「欄」為單位判定，某欄只要有**任何一列**被保護
就算整欄受保護。若某分頁只做了局部保護（例如只保護 `O3:O8`），**會被誤判為安全**。
發現輸出裡有 `T3:T8` 這類局部範圍時，要人工確認是否另有整欄保護蓋住。

**最終驗收方式**：用另一個同事的帳號打開試算表，試著手動修改某分頁的簽核欄 → 應該被拒絕。
這是唯一能證明保護真的生效的方法，工具只能告訴你「設定看起來對」。

## 四、GAS 專案設定

### 4-1 建立專案並貼入程式

兩支檔案要放在**同一個 Apps Script 專案**（notify 會呼叫 approval 的函式）：

1. 到 [script.google.com](https://script.google.com) 建立新專案，命名為「發包簽核」
2. 貼入 `gas-dispatch-approval.gs`
3. 左側「檔案 +」新增指令碼，貼入 `gas-dispatch-notify.gs`

### 4-2 指令碼屬性

專案設定 → 指令碼屬性：

| 屬性 | 必填 | 值 |
|---|:--:|---|
| `DISPATCH_SHEET_ID` | ✅ | 試算表網址 `/spreadsheets/d/` 後面那一段 |
| `DISPATCH_SHEET_NAME` | ✅ | 分頁名稱。三種寫法見下 |
| `DISPATCH_HEADER_ROW` | | 表頭在第幾列。留空會自動偵測（找含「發包單號」的列） |
| `DISPATCH_PENDING_SINCE` | | 只列出申請日 ≥ 此日期的（`YYYY-MM-DD`）。留空＝不過濾 |
| `DISPATCH_CHAT_WEBHOOK` | | Google Chat 傳入 Webhook 網址 |
| `DISPATCH_WEBAPP_URL` | | 部署後回填（見 4-3） |
| `DISPATCH_SNAPSHOT_FOLDER_ID` | | 每日備份存放的 Drive 資料夾 ID，留空＝不備份 |
| `DISPATCH_SNAPSHOT_KEEP` | | 保留幾份備份。留空＝全部保留、不自動清理 |
| `DISPATCH_SUB_APPROVERS` | | 副主管的 Google 帳號（逗號分隔）。見下方⚠ |
| `DISPATCH_BOSS_APPROVERS` | | 主管的 Google 帳號（逗號分隔）。見下方⚠ |

> ⚠ **兩層簽核若不設名單，兩層覆核形同虛設。** 名單留空＝機構內任何人都能核，
> 同一個人可以先按副主管層、重新整理後再按主管層，自己把兩層都核完——
> 那只是同一個簽名蓋兩次，比單層更糟，因為看起來像有覆核。
> 系統仍會運作（導入初期還沒收集到 email 就全擋會直接不能用），
> 但 `checkSetup` 會警告，且稽核紀錄會標記這個降級狀態。

#### `DISPATCH_SHEET_NAME` 的三種寫法

實際的試算表是**每位業務一個分頁**（`零售-Johnson`、`零售-Sammi`…）：

| 寫法 | 效果 |
|---|---|
| `零售-Johnson` | 只讀這一個分頁 |
| `零售-Johnson,零售-Sammi` | 讀這幾個分頁（逗號分隔） |
| `*` | **自動掃描所有分頁**，凡是含「發包單號」表頭的都納入 |

> **建議用 `*`**。只設一個分頁的話，其他業務的發包主管會看不到，而且是**安靜地看不到**
> ——沒有錯誤訊息，只是清單裡少了東西，這是最難察覺的失效。
> 用 `*` 之後新增業務分頁也不必改設定。

自動掃描的排除規則：

| 情況 | 處理 | 例子 |
|---|---|---|
| 沒有「發包單號」表頭 | 靜默略過 | 人員代碼 |
| 分頁名為「簽核紀錄」 | 強制排除 | 它的表頭也有「發包單號」，不排除會把稽核紀錄讀成待核項目 |
| 有「發包單號」但**缺「主管簽核」欄** | **整個分頁略過並在 `checkSetup` 大聲警告** | 見下 |

> ⚠ **缺「主管簽核」欄的分頁一定要處理。** 沒有那一欄，程式判斷不出哪些已核，
> 會把**整張表所有列都當成待核**（實測某分頁一次灌進 151 筆）；就算主管按了核准
> 也沒有欄位可以寫。因此這種分頁一律略過，並由 `checkSetup` 列名警告。
> 補上欄位，或確認該分頁的欄名是否與其他分頁不同。

#### `DISPATCH_PENDING_SINCE` 什麼時候要設

現有資料裡有 **2023 年的單一直沒填簽核欄**。那多半是歷史遺留，不是真的等著被核。
主管打開頁面看到一堆三年前的單，會失去對這個工具的信任。

設成例如 `2026-01-01`，就只列出今年以後的。
預設不過濾——不替你決定哪些資料該被藏起來，但你應該要知道有這個選項。

### 4-3 部署為網頁應用程式

部署 → 新增部署作業 → 類型選「**網頁應用程式**」：

| 設定 | 值 | 為什麼 |
|---|---|---|
| 執行身分 | **我（擁有者）** | 才有權寫入受保護範圍 |
| 具有存取權的使用者 | **機構內的任何人** | 才拿得到登入者身分 |

> ⚠ **絕對不要選「知道連結的任何人」**。那樣 `getActiveUser()` 會回空值，
> 系統無法辨識簽核者，程式會直接拒絕簽核（這是刻意的防護，不是 bug）。

部署完成後複製網址，回填到指令碼屬性 `DISPATCH_WEBAPP_URL`。

### 4-4 Google Chat Webhook

1. 在要收通知的 Chat **空間**（Space，不是一般群組聊天）
2. 空間名稱旁「⋯」→ 應用程式與整合 → 管理 Webhook → 新增
3. 命名「發包簽核通知」→ 複製網址 → 填進 `DISPATCH_CHAT_WEBHOOK`

### 4-5 觸發器（人工建立，本專案慣例不由程式自動建）

左側時鐘圖示 → 新增觸發條件：

| 函式 | 類型 | 頻率 |
|---|---|---|
| `notifyPendingApprovals` | 時間驅動・日計時器 | 上午 9–10 點 |
| `dailySnapshot` | 時間驅動・日計時器 | 凌晨 1–2 點 |

## 五、驗收清單

部署前先在編輯器手動執行兩支自檢函式，看執行記錄：

- `checkSetup()` — 檢查試算表設定、欄位是否齊全、列出待核筆數
- `checkNotifySetup()` — 檢查通知與備份設定，並實際送一則測試訊息到 Chat

部署後逐項驗證：

| # | 驗證項目 | 預期結果 |
|---|---|---|
| 1 | 用 A 帳號開簽核頁按核准 | 簽核欄記錄的是 **A 的 Google 帳號**，不是任何手打值 |
| 2 | 同事手動編輯簽核欄 | **被拒絕**（受保護範圍生效）|
| 3 | 兩人同時開頁面、都按同一筆 | 後按的人看到「這筆已經被處理過了」，不會覆蓋 |
| 4 | 退回但不填原因 | 被擋下，要求填寫 |
| 5 | 簽核紀錄分頁 | 每次核准／退回都有一列，含時間、操作者、層級、原因 |
| 6 | Chat 通知 | 收到訊息、連結可點開、兩層筆數各自正確 |
| 7 | 每日備份 | 指定 Drive 資料夾出現副本；手動刪一列後可從副本還原 |
| 8 | 待核為 0 時 | **不發通知**（不吵人），執行記錄寫「本次無待核項目」 |
| 9 | 兩層分頁：副主管核准後 | 該筆從「副主管待核」移到「主管待核」，主管欄仍空 |
| 10 | 兩層分頁：副主管退回 | 該筆完全消失，**不進主管清單**；狀態寫「已退回（副主管）」|
| 11 | 同一人連續核兩層 | 第二層**被拒絕**（不在該層名單）——這是兩層覆核的意義所在 |
| 12 | 主管層卡片 | 看得到「副主管」那一列，知道是誰核過的 |

> 第 11 項是整套兩層簽核最該驗的一項。若它沒被擋下，代表 `DISPATCH_SUB_APPROVERS`／
> `DISPATCH_BOSS_APPROVERS` 沒設好，兩層覆核等於沒有。

階段二要做發包單號自動編號時，需要新增一張「人員代碼」分頁：

## 七、已知限制

- **TipTop 無法串接**（EasyFlow 授權洽談中）。訂單、出貨單都得人工鍵入 ERP，
  出貨單號也得人工回填試算表。本方案不假裝能解決這件事。
- **Teams 無法自動化**。公司使用的是個人 Microsoft 帳號（非組織租戶），
  沒有團隊/頻道、也沒有 Graph API 存取權。階段三最多做到「一鍵複製貼上」。
- **試算表的先天限制**：多人同時編輯有並發風險（程式端已用 `LockService` 保護寫入，
  但人工編輯無法防）；GAS 每日執行時間 6 小時（Workspace 帳號），以目前單量綽綽有餘。
