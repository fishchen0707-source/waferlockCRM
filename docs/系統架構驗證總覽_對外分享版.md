# 客服／派工 CRM 系統架構驗證總覽（對外分享版）

> 本文件整理一套「從零自建、已實際驗證可運作」的客服與到府服務 CRM 系統架構，
> 供技術交流參考。文中已移除所有公司識別資訊、金鑰、網址與營運數據；
> 情境設定為「販售需到府安裝之硬體產品的品牌」（如智慧門鎖、家電等皆適用）。

---

## 1. 整體架構

```
┌────────────── 管道層（只做協定轉換）──────────────┐
│  LINE OA │ FB/IG │ 0800語音 │ Email │ 網頁表單 │ AI語音 │
└──────────────────────┬───────────────────────────┘
                       ▼
┌────────────── 進件層（統一入口）──────────────────┐
│  金鑰驗證｜客戶識別（地址=客編唯一鍵）｜初分類     │
└──────────────────────┬───────────────────────────┘
                       ▼
┌────────────── 資料層（單一事實來源）──────────────┐
│  客戶主檔 ── 工作項（維修/安裝/客訴）── 對話串     │
│  PostgreSQL（Supabase）＋ Storage（照片/錄音）    │
└──────────────────────┬───────────────────────────┘
                       ▼
┌────────────── 介面層（同一份資料的不同視角）──────┐
│  客服台 │ 派工管理台 │ 師傅端 │ 客戶端(LIFF/網頁) │
└──────────────────────────────────────────────────┘
```

核心方法論借自 ITSM：**任何管道進來的請求都是一張工作項（ticket），走同一條生命週期**——
未處理 → 處理中 → 待客戶 → 已完成，已結案者收到新訊息自動翻回未處理。

---

## 2. 技術棧總覽

| 層 | 選型 | 備註 |
|----|------|------|
| 前端 | 單一 HTML ＋ React 18 CDN ＋ Babel Standalone | 零建置工具，改完存檔即生效；適合小團隊快速迭代 |
| 靜態部署 | GitHub Pages | push 即自動部署 |
| 資料庫 | Supabase（PostgreSQL ＋ Realtime ＋ Storage ＋ Edge Functions） | 免自架後端 |
| 後端邏輯 | Supabase Edge Functions（Deno/TypeScript） | webhook、推播、外部進件 API |
| 排程任務 | Google Apps Script（時間觸發器） | Email 掃信進件等 |
| 語音/STT | WebRTC ＋ Python FastAPI worker（見 0800 技術棧文件） | gRPC 需求無法跑在 Deno，另立 Python 服務 |
| AI | 大型語言模型 API（文字客服、語音對話、通話摘要） | function calling 查單/建單 |

**取捨說明**：這套組合的最大特徵是「零建置、零伺服器維運」，代價是前端為
development build、單檔巨大（3000+ 行）。適合驗證期與中小規模，放量後應演進至正規前端工程。

## 3. 已驗證的子系統

### 3.1 客戶主檔與客編中心

- **客編唯一鍵＝正規化地址＋姓名**（電話「非」唯一鍵——同一支電話可能對應多個住所，
  以電話歸戶會把房東多戶誤併成一戶）。全形轉半形、「臺→台」、去空白後比對。
- 案件發生當下即發客編（流水號 RPC 取號），查無客戶自動建「待整理」暫存客戶，
  後續可依地址一鍵重新歸戶（冪等）。

### 3.2 三類工作項與統一生命週期

| 類型 | 編號 | 狀態機 |
|------|------|--------|
| 客訴 | C+日期+流水 | 待處理 → 追蹤中/已派工 → 結案（結案時才填三層分類，供報表） |
| 維修 | R+日期+流水 | 待處理 → 已派工 → 完工結案 |
| 安裝 | IW+時間戳 | 待出貨 → 已出貨 → 排程 → 到場 → 施工完成 → 驗收完成 |

- 客訴卡片單一下拉選單分流：轉維修／轉安裝／排追蹤（datetime）／線上結單。
- 每次狀態異動寫入 `history` JSONB 陣列（時間、操作者、動作），含**轉單改派**
  （師傅臨時無法前往 → 改派他人，記錄「原師傅→新師傅＋原因」）。

### 3.3 派工排程（工務時刻表）

- 分區（北/中/南）× 每師傅每日 13 個小時格；維修佔 1 格、安裝佔 2 格。
- 佔格資料表以 `(worker, date, hour)` 唯一約束防撞單；插入衝突即回報「時段已被佔用」。
- 轉單時先記住舊時段，新時段衝突則自動還原，避免「單子顯示已派工、時刻表卻空著」的中間態。

### 3.4 完工驗收與金流尾段

- 驗收 Modal：現場照片（Storage）＋客戶簽名（Canvas）＋功能驗收 checklist＋操作教學確認
  ＋簽收單號＋保固自動起算。
- 收費品項表（品名×數量×單價＋贈品）、收款方式、開票資訊（發票類型/統編/抬頭，三聯必填驗證）。
- 出貨閘門：安裝單未登記 ERP 出貨單號前，排程按鈕鎖定（既有已排程單不回溯）。
- 請款狀態單向推進：待請款 → 已請款 → 已開票，每步留異動紀錄。

### 3.5 多管道整合收件匣

- LINE / FB / IG / 電話 / Email / 網頁 統一進 `conversations` 表，平台徽章＋分頁篩選。
- webhook（LINE Messaging API、Meta Graph API）皆做**簽章驗證**（HMAC-SHA256）。
- **訊息陣列原子 append**：所有寫入方（多支 webhook、前端、worker）統一走一支
  PostgreSQL RPC：`INSERT ... ON CONFLICT DO UPDATE SET msgs = msgs || 新訊息`。
  這是本系統踩過最深的坑——原本「讀出陣列→程式內 append→整包寫回」在並行寫入時
  會互相覆蓋、訊息無聲消失；改為單一原子陳述式後，資料庫列鎖天然序列化。

### 3.6 師傅端（外勤 App）

- 手機網頁：登入接案 → 回報預計抵達（ETA 自動推播客戶 LINE）→ 到場 → 施工
  → 拍照上傳 → 客戶簽名 → 收款回報 → 完工結案。
- 推播雙軌：先寫進客戶對話（後台可見），客戶有綁定 LINE 才另發真實推播；
  失敗顯性提示，不靜默。

### 3.7 AI 客服（文字＋語音）

- 文字：LLM 依知識庫回答，語意不確定轉真人；真人接手後 AI 靜默。
- 語音：即時語音對話（詳見 0800 技術棧文件），LLM function calling 落地兩個工具：
  `查詢工單進度(電話)`、`口頭報修建單(姓名/地址/問題)`——確定性邏輯（查表、狀態碼
  轉中文）由普通程式處理，不交給模型。

### 3.8 外部進件 API

- 單一 Edge Function 收「網頁諮詢單」與「Email 進件」：
  - **雙金鑰設計**：主金鑰（後端用，全能）＋表單金鑰（前端網頁用，權限收窄到
    只能建諮詢單——前端金鑰必然公開，外洩頂多被灌諮詢單）。
  - 網頁表單含 honeypot 隱藏欄防機器人。
  - Gmail 進件：Apps Script 定時掃指定標籤未讀信 → 呼叫 API 建單 → 貼「已進件」標籤；
    失敗不標已讀，下次觸發自動重試。

### 3.9 深層連結與即時同步

- Hash routing（`#crm/客編/案號`）：每張工單可分享直達連結，GitHub Pages 原生支援。
- Supabase Realtime 增量同步：訂閱 `postgres_changes`，依表/事件只更新受影響的
  單筆記錄（初版每次事件全量重拉 10 張表，流量爆炸，增量化後根治）。
- 全量載入分頁化：PostgREST 預設單次最多回 1000 列，用 `.range()` 迴圈抓到底，
  避免資料成長後「無聲消失」。

## 4. 資料設計要點

- **JSONB 優先於加欄位**：追蹤排程、派工連結、異動紀錄都塞進既有 JSONB
  （`timeline`/`history`），大量功能免 schema migration。
- **流水號 RPC 取號**：案號/客編由資料庫函式產生（含日期前綴＋流水），
  前端 fallback 用時間戳（並知道 Supabase client 失敗不丟例外，要檢查回傳的 `.error`）。
- **顯性失敗原則**：所有同步寫入逐一檢查 `.error`，失敗跳 toast＋同步燈號轉離線；
  初始載入失敗顯示錯誤畫面＋重試按鈕，絕不假裝空資料庫正常（否則客服會重複建檔）。
- **照片走 Storage 不進資料列**：base64 塞資料列曾讓單次載入 21MB/7 秒，
  遷移 Storage 後 127KB/0.3 秒。

## 5. 踩坑清單（最有價值的部分）

1. **Supabase client 失敗不丟例外**——`try/catch` 包 `.upsert()` 抓不到 RLS 拒絕、
   欄位錯誤；必須檢查回傳物件的 `.error`。
2. **並行寫 JSONB 陣列必用原子 RPC**（見 3.5），read-modify-write 必丟資料。
3. **PostgREST 1000 列預設上限**是定時炸彸，上線前就要分頁。
4. **`onClick={fn}` 會把 event 物件當參數傳入**——`onClose(newId)` 型 callback
   被 event 誤觸發，用 `onClick={()=>fn()}` 顯式無參呼叫。
5. **webhook 對事件逐一 try/catch 後回 200**，平台不會重送，失敗訊息永久遺失——
   要嘛整批失敗回 5xx 讓平台重送（需冪等），要嘛失敗落地重試佇列。
6. **Realtime 回聲會覆蓋本地未同步的第二次編輯**——樂觀更新＋last-write-wins
   對快速連續操作不安全，重要欄位改原子 RPC 或版本檢查。
7. **釋放舊資源再佔新資源的兩步操作**（如改派時段）必須做失敗回滾，
   否則卡在「兩邊都沒有」的中間態。

## 6. 安全注意（驗證期已知妥協，上線前必補）

- 驗證期為求速度採「RLS 全開＋前端閘門」與 anon key 直連——**正式上線前必須**
  收緊 RLS、密碼改雜湊、統一身分與角色權限。
- 對外 API 一律金鑰驗證＋權限最小化（見 3.8 雙金鑰）；webhook 一律驗簽章。
- 個資去識別化工具（客服對話匯出訓練/分析用）：姓名保留頭尾遮中間、電話留前4後3、
  地址保留縣市區、統編/公司抬頭部分遮罩，姓氏白名單避免誤遮常用詞。
